# Architecture

MNG Review reviews a change with a main reviewer and the agents a repository declares, then tries to refute every bug finding before it reports it. The behaviour is specified in `docs/spec.md`; this file maps it onto the code. Terms are defined in `UBIQUITOUS_LANGUAGE.md`.

## Layout

```
apps/
  cli/                     @mng-review/cli: the mng-review binary
    src/main.ts            the only file that runs effects (BunRuntime.runMain)
    src/presentation/      effect/cli commands and output formatters
  action/                  @mng-review/action: the GitHub workflow entry, shadow mode and the steps of publish mode
    src/main.ts            the only other file that runs effects
    src/application/       the shadow run (event, gate, probe, review) and the publish run
    src/infrastructure/    event parser, runner client (summary, masks)
    src/presentation/      job summary formatters
packages/
  domain/                  @mng-review/domain: Schema and pure logic
  engine/                  @mng-review/engine: Effect services
    src/platform/          config, llm, git
    src/modules/           routing, review, validation, risk, converse, init, bench
  github/                  @mng-review/github: the GitHub API and publishing, used only by the action
    src/platform/          config and the bot identity, the REST and GraphQL client on effect/http
    src/modules/command/   the mention command grammar and who may run a command
    src/modules/publish/   which findings get a thread, comment and summary text, posting, re-check
    src/modules/status/    check runs, the MNG Review commit status, the status sweep, the raise
    src/modules/risk/      the risk status, its write order, the risk marker and labels
tooling/
  typescript-config/       @mng-review/typescript-config: the strict tsconfig preset
  oxlint-plugin/           @mng-review/oxlint-plugin: the mng-review/* lint rules
docs/
  spec.md                  the design
  decisions/               architecture decision records
```

`.github/workflows/review.yml` is the reusable workflow that runs `apps/action`.

## Package layering

Dependencies point one way: `apps/cli` and `apps/action` → `packages/engine` → `packages/domain`, and `apps/action` → `packages/github` → `packages/engine`. A package never imports an app, and an app never imports another app.

| Package  | May use                                                                    | Never                                                                              |
| -------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `domain` | `effect` (`Schema`, `Data`, `Predicate`, pure modules)                     | services, layers, I/O, a runtime                                                   |
| `engine` | `domain`, `effect` and its `cli`-free modules, `@effect/ai-openai-compat`  | running effects, printing to the terminal                                          |
| `cli`    | `engine`, `domain`, `effect/cli`, `@effect/platform-bun`                   | review logic                                                                       |
| `github` | `engine`, `domain`, `effect/http`                                          | review logic, running effects                                                      |
| `action` | `engine`, `domain`, `github`, `@effect/platform-bun`; a step's layers only | review logic, GitHub API calls of its own, GitHub in the step that calls the model |

Inside `engine`, `platform/` holds what every module shares and `modules/<module>/` holds one stage of the pipeline, split into `application/` (services, ports, model tools) and `infrastructure/` (adapters and parsers). ADR 0001 records the layout and ADR 0003 the file names.

## Pipeline

One run of `mng-review --base <ref>` goes through these steps. Numbers match the pipeline in `docs/spec.md`.

1. The CLI parses its flags and provides the engine's layers in `main.ts`.
2. `platform/config` reads `.mng/review.yml`, `.mng/CONTEXT.md`, `.mng/MEMORY.md` and `.mng/agents/*.md` from the working tree, or from `--rules-ref`, and decodes them with the schemas in `domain`. Unknown keys fail the run.
3. `platform/git` reads the change between the merge base and the head: changed paths, renames, the diff and file contents at a ref.
4. Gate (1): `domain` helpers apply `skip` and `features`.
5. Route (2): `modules/routing` selects agents by `when` rules, then asks the router model for agents to add and a risk level. A router failure falls back to path selection and `normal`.
6. Depth (3): the risk level or `depth` picks how many reviewer models run and whether the change is split into units.
7. Find (4): `modules/review` runs the main reviewer and each selected agent as a tool loop on `effect/ai`, with read-only tools over the repository. Findings with the same root cause merge. The review service sizes each main reviewer conversation by what it must read before it runs the finders (`reviewer-jobs.helper.ts`, within `limits.tokens_per_run`), the loop grows that grant by the conversation's token rate after its first call (`loop-budget.helper.ts`), and the main reviewer gets one continuation turn when it answers before receiving every changed file whole; the files it leaves unread go into the report with their reasons.
8. Validate (5): `modules/validation` runs one fresh agent per bug finding to refute it, on a reviewer model that did not report it when `validator: cross`. A finding every reviewer model reported, or a run with one reviewer model, is validated once by a reviewer model in a fresh context. Nearby bugs from different finders are validated as a group, and the validator decides which of them are one defect.
9. Rate: with `risk.enabled` on a full run (`isRatingRun`), `modules/risk` reads the floor diff (`FloorDiffService`, `git diff --no-renames --raw --numstat -z` through `parseFloorDiff`) and, unless the review failed or a binary outside `risk.assets` changed, runs `RaterService`: one agent on `risk.model` through `AgentLoopService` with `RATER_REPO_TOOLS` and `report_risk`, over the unfiltered change, held to the loop's read coverage. The report carries the result as `rating`; publish recomputes the floors from its own git read.
10. The CLI formats the kept findings and the rating as text or JSON; the workflow entry writes them to the job summary.

Steps 2 to 9 run through `ReviewRunService` in `modules/review`, so the CLI, the benchmark and the workflow entry review a change the same way.

Publish (6) runs in the workflow's publish mode through `packages/github`; learn (8) follows.

Converse (7): `ReplyService` in `modules/converse` decides on an author's reply in one of the bot's threads. One fresh agent on a validator model, through `AgentLoopService` with the validator's read tools and `report_reply` as its finish tool, reads the claim; a `fixed` claim goes to `RecheckService` without the reply's text, and an `intentional` claim's evidence is checked in git. The decision itself is the pure `toReplyDecision` in `domain/src/converse`, with `getIntentionalLimit` and `toMemoryCandidate`. `makeReplyLayer` builds the service on the endpoint, like `makeValidatorLayer`. It reads no GitHub data: the action collects the replies (`ThreadReplyService.collect`) and publishes the decisions, in push and command runs and on the reply schedule (`review-converse.yml`, below).

## GitHub workflows, shadow and publish mode

`.github/workflows/review.yml` checks out the caller's base commit (history only; the head commit is fetched as objects, never checked out) and this repository at the workflow's own commit, installs it with `--production --ignore-scripts`, optionally joins a tailnet, and runs `apps/action/src/main.ts` in the caller's checkout. `ShadowRunService` reads the event, skips forks before anything else, loads `.mng/` from the base commit, applies `skip`, asks `EndpointProbeService` for `GET /models`, and reviews base..head through `ReviewRunService`. The summary formatter escapes every text that came from a model or the repository. The result formatter writes the same outcome as JSON, with the review document `mng-review --json` prints (`toReviewJson` in the engine), and the workflow uploads it as the `mng-review-result` artifact. Nothing is posted. ADR 0006.

`review-publish.yml` runs two jobs that meet only through the outcome file. The `review` job has a read-only token and the endpoint secrets and runs `.github/actions/review` in publish mode, which is two steps of the entry. The prepare step (`MNG_REVIEW_MODE=prepare`) gets the read token and no endpoint variable: `PrepareRunService` makes the checks shadow mode makes before the probe, reads the summary's marker for `limits.max_runs_per_pr` and incremental input, reads the bot's threads (a GitHub error counts as none), collects the authors' replies in them through `ThreadReplyService.collect` (latest comment by a writer, at most eight), and writes the prepared file (`prepared-run.schema.ts`) into `RUNNER_TEMP` and the step output `ready`. A run the checks skipped never joins the tailnet. The review step (`MNG_REVIEW_MODE=review`) runs with `GITHUB_TOKEN` and `GH_TOKEN` empty and builds no GitHub layer: `ShadowRunService.review` loads the rules again and reviews, and `ThreadRecheckService.propose` hands the prepared threads whose file changed to the engine's `RecheckService` (the validator over the change from the thread's commit) and returns the ones it rejects as proposals; `ReplyDecisionService.decide` then hands the prepared replies to the engine's `ReplyService` on the same token ledger. The entry turns the outcome and the proposals into the outcome file (`outcome-file.schema.ts`, redacted like the result file), writes it to `MNG_REVIEW_OUTCOME_PATH`, and sets the step output `publish` for a reviewed run the plan did not skip and for an offline endpoint; the action uploads it as `mng-review-outcome` for a day. The `publish` job has the write token and no endpoint or tailnet secret, and runs `.github/actions/publish`: it downloads this run's outcome and result, and the publish step (`MNG_REVIEW_MODE=publish`) parses the file with the schema (`reviewReportSchema` in `packages/github` for the report), checks its binding (repository, run, attempt, engine commit, pull request, base and head) against its own runner and event, and exits 1 without posting when the file is missing, too large, invalid or bound elsewhere. `PublishRunService` publishes from the parsed file alone, loads the rules again from the base commit, and calls no model. It hands the report and the proposals to `PublishService` in `packages/github`: it reads the bot's threads through `GitHubApiService` and the summary through `SummaryReviewService` (reviews through `GitHubReviewService`, old sticky comments for migration), applies the proposals through `ThreadResolutionService`, which resolves only threads its own fresh read still shows open, unanswered and on the proposal's fingerprint, and the reply decisions through `ThreadReplyService.apply`, which answers only while the decided comment is still the thread's latest, after `ReplyCheckService` checks each `resolved` and `accepted` decision with its own git reads (the `fixed` gate, and the evidence through the engine's `ReplyEvidenceService.checkInCode`), keeps the threads waiting for the owner in the summary marker and syncs the `needs-owner` label (`ThreadSettleService` marks an answer `unsettled` until the reopen after it lands, settles earlier unsettled answers, and keeps a wait whose newest app answer is unsettled), folds `git diff` of merge base..head into the lines GitHub accepts comments on, plans the threads with the pure helpers in `modules/publish/domain` (published findings, duplicates, places), posts comments on whole files, then writes one review whose body is the summary, whose comments are the line threads and whose state is `getReviewDecision`'s from the evidence the run carries (`getCoverageGap` for an approval, from the report's skipped files, budget stops, failed runs and the main reviewer's `unread` count, and the head read again), headed by `formatReviewHeadline`, or edits its last review's body when it posted nothing and the state stays, never an approval or change request on an older commit (ADRs 0010, 0011); `ReviewDismissService` then dismisses the owned change requests a clearing write leaves stale and the owned approvals that outlived their head. `StatusReportService` then writes a check run per agent and the commit status, and the step adds `publish` to the result file. `main.ts` provides each mode only the layers it needs, so the review step cannot reach GitHub and the prepare and publish steps cannot reach the model. `status-sweep.yml` runs the entry with `MNG_REVIEW_MODE=sweep`, which loads the rules from `HEAD` of a default branch checkout, and only lowers statuses; the reply schedule's `raise` job writes `success` and dismisses the current identity's change requests (below). A comment someone else edited is no longer the bot's. `GitHubConfig` holds the token and the bot identity it posts as: `GitHubWriteConfigLive` (publish, sweep) picks the job token or, with `MNG_REVIEW_APP_SLUG`, the app token and checks it against the minted slug; `GitHubReadConfigLive` (prepare) always reads with the job token. Once the rules are loaded, the entry provides `OwnedIdentities` (the token's identity and `identity.previous`), which the thread helpers, `SummaryReviewService` and `getStatus` read; every summary write hides the earlier reviews of owned identities and old sticky comments as outdated. ADR 0009. Shadow mode builds no GitHub layer and never reads a token. ADR 0007.

`review-command.yml` runs a mention command in four jobs. `authorize` (`MNG_REVIEW_MODE=authorize`) parses the `issue_comment` event, loads the rules from the default branch and asks `CommandAuthorizeService` in `packages/github` (`parseMentionCommand`, the role, the pull request and `commands.max_runs`) over the read token; a refused comment is a denial and the step passes, except a failed role or cap read for the rating's checks, which fails the job (ADR 0012). It writes the outputs the later jobs start from. `reserve` (`MNG_REVIEW_MODE=reserve`) reads the pull request again, runs `PrepareRunService` for the base commit's gates and counts the run with `SummaryReviewService.reserveManualRun` over the write token. `review` and `publish` run the publish-mode steps with `MNG_REVIEW_TRIGGER=command`: the prepare step and the publish step read the pull request named by `MNG_REVIEW_TARGET_*` again instead of the event, the review step passes the named agent and the requested depth, and the publish step marks a run of one agent as partial. ADR 0009.

`review-converse.yml` answers replies on a schedule from the default branch, or through `workflow_run` after the caller's secretless signal on a reply. `find` (`MNG_REVIEW_MODE=find`) loads the rules from `HEAD` of the default branch checkout and asks `ReplyFindService` in `packages/github` over the read token for the open, same-repository pull requests with a counting reply (`ReplyFindService.readPending`: the threads first, then, only where a reply may count, the waiting list from every owned summary review and old summary comment and the bot's `needs-owner` answers and `ThreadReplyService.collect`), at most `MNG_REVIEW_MAX_PULL_REQUESTS`, and writes them as the step output `pulls`, the matrix of the next jobs; a failed list or a read that failed on every pull request exits 1. It also asks `RaiseService.findDue` for the pull requests whose planned status differs from the bot's status or whose current-identity change request nothing backs any more, beside the reply scan, making at most `RAISE_SCAN_LIMIT` full judgments, starting up to that many pull requests further each run number (`getScanStride`), always judging the one at its start and starting no later judgment past `RAISE_SCAN_DEADLINE` (a started judgment runs to its end) and ending the whole scan, its listing included, at `RAISE_SCAN_BOUND` (finished judgments are kept, the one in flight is dropped and named, and the warning says where the bound cut), and capped in that order, judged by `PullStateService`, the reads and judgment the status sweep shares, and writes them as `raises`; a failed raise listing keeps the replies and prints a warning. The `raise` job (`MNG_REVIEW_MODE=raise`) runs after the publish legs in each pull request's publish group and calls `RaiseService.raise`, which judges the pull request again from one read, checks that it is still open and the head and the status again, and writes `success` and dismisses through `ReviewDismissService.liftRequests` only while a raise is still due. Between runs it is the only place that raises (runs raise in their publish jobs, inside the same group); it also rewrites a blocking status whose plan changed, and `StatusSweepService` only lowers (`toLoweredStatus`). `review` and `publish` run the publish-mode steps with `MNG_REVIEW_TRIGGER=converse`: the prepare step reads the pull request again, skips the gates but drafts and a new head or base, and reads the replies with `readPending`, the review step runs `ConverseRunService` (the probe, then `ReplyDecisionService` only), and the publish step hands the decisions to `ReplyPublishService`, which applies them with the push publish's checks (the change read from git through `ThreadPlaceService.readChange`, never from the outcome file) and changes only the verdict line and waiting list of the summary, by editing the newest review or posting a new one. A pull request that closed, became a draft or moved to a new head or base since `find` listed it gets nothing, and the step passes. ADR 0009.

The rating in publish (ADR 0012): `PublishRunService` gates the run with `getRiskGate` (`risk.enabled`, the app, `MNG_REVIEW_APP_ENVIRONMENT`, a pull request into `MNG_REVIEW_DEFAULT_BRANCH`), and `RiskRunService` wraps the publish. For a full run `RiskStartService` in `packages/github` reads the held level (`RiskReadService.readHeld`), the marker and the floors from its own git read, writes step 1's `error` and reads it back before anything is posted, and the step puts its description out as `risk-description`; after the post `RiskFinishService` checks its nonce, updates the marker (reading the comment's edit history around the write and matching edits by id), sets the label through `RiskLabelService`, makes the re-checks and writes the grant last, then reads it back. A thread run posts first and then raises through `RiskStartService.startThread`. `MNG_REVIEW_MODE=risk-cleanup` runs `RiskFinishService.revokeHead` with that description after a failed or cancelled publish step.

Answers (ADR 0012): `AnswerReadService` in `packages/github` reads the commands on a pull request with their authors' roles and the entries of the current app's answers (`reply`, `summary` and `answer` markers its current identity wrote and no one else edited), and gives a rating review its entry; `PublishService` appends it to the summary marker after the earlier ones (`toAnsweredMarker`). `ReplyNamingService` decides which replies a converse answer names, and the thread reply's marker carries them. `CommandAnswerService.check` runs in the authorize step after `CommandAuthorizeService`: a `review` past `risk.reviews_per_head` becomes a cap reply and a refused command from an acted-on author a denial, both handed out as step outputs. `MNG_REVIEW_MODE=deny` (`CommandAnswerService.post`) posts that reply with an `answer` marker over the write token, outside the per-pull-request group; a failed read or post fails the job.

The sweep's rating part (ADR 0012): with the rating on, the `sweep` step also lists the open pull requests through `listRiskPulls` (`GitHubStatusService.listOpenPullRequests` with `complete`, which fails past its page limit) and puts them out as `risk-pulls`, failing on more than `RISK_MATRIX_LIMIT` (256). `MNG_REVIEW_MODE=risk-sweep` takes one pull request (`MNG_REVIEW_TARGET_PR`): `RiskRunService.rateThread` raises its status, and `RiskSweepService.sweepPull` reads the comments that may hold through `SweepCandidateService.gather`, then the review workflow's runs from the oldest of them (or from the head's arrival) and their jobs through `GitHubRiskService` (`listRuns`, `listRunJobs`), picks the holding comment with `SweepCandidateService.choose`, decides with the pure helpers in `modules/risk/domain` (`sweep-hold`, `sweep-run`, `sweep-dispatch`) and dispatches at most one run. The step hands it the checks per dispatch kind (`getSweepChecks`, which runs the review job's own gate, `getGateReason` over `toCommandEvent`).

## Init

`mng-review init` writes `.mng/` at the repository root. The starter files and the conversion from `.macroscope/` are pure functions in `domain/src/init`; `modules/init` reads `.macroscope/` through the same confined working-tree reader as the rules, loads every generated `review.yml` and agent file as `RulesService` does (imports expanded), refuses symlinks on the way to its targets, and only then writes. It never runs a model.

## Bench

`mng-review bench` parses the benchmark file with the schema in `domain/src/bench`, loads the rules once, then plans and reviews each case with the same services as a review, each case on its own token ledger and review layer. Matching and totals are pure functions in `domain/src/bench/bench.helper.ts`.

## Model endpoint

`platform/llm` builds one OpenAI-compatible client from `MNG_REVIEW_LLM_URL` and `MNG_REVIEW_LLM_KEY` (read with `Config.Redacted`). Every role uses it with the model and effort from `models` in `review.yml`. A model that answers 429, 503 or "unknown model" is dropped for the rest of the run. Specs replace the endpoint with a test layer.
