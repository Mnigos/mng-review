# ADR 0012: The risk rating is a commit status the app grants last

**Status:** Proposed; amends ADR 0009's rule that an edit starts nothing
**Date:** 2026-11-24

## Context

A repository can let a merge tool merge low-risk pull requests without the owner. Today a person or an agent sets a risk label, and anyone with write access can set a label. The rating then decides what merges without the owner, so it is a permission: it must come from a writer the pull request cannot impersonate, it must never walk down, and it must be revoked before anything that could change it is written. A model rates the change, and the change is text that can argue for a lower level, so the paths that matter most cannot depend on the model. GitHub keeps every commit status and cannot delete one, so statuses can carry history; a status sits on a commit, while two pull requests can share a head.

## Decision

- **The permission is a commit status.** The app writes `MNG Review risk` on the head: `success` at Low and Medium, `failure` at High, `error` when not rated. Its description has exactly one form, `v1 pr=<n> <low|medium|high|none> floor=<yes|-> base=<40 hex> rules=<12 hex> nonce=<16 hex>`, at most 121 characters. Every reader takes only the app's statuses whose `pr` is its own pull request, and rejects any other text. Only `success` at `low` or `medium` grants. The label is display only, and `MNG Review risk` is never a required check, so the owner can still merge by hand.
- **Only the app rates, from an environment.** A run rates only with `app-slug` and `app-environment`. The app key lives in an environment whose deployment branches are the default branch only, so a pull request's own workflow is refused it. Jobs that hold the key check out the base commit only, read the head as git objects, give the model read-only tools and pass event text through environment variables or files.
- **The rater** is a step after Validate. It reads the rubric (`.mng/risk.md` and its imports, from the base commit), the complete file list, the budgeted diff, the kept findings, the floors that applied and the previous rating, never the title, description, comments or commit messages. A rating counts only when every changed hunk was in its prompt or in ranges it read, every finder of the review finished, and the token budget did not force the rater's answer.
- **Floors come from the complete change.** Publish runs `git diff --no-renames --raw --numstat -z` itself; a rename counts at both paths. The built-in floor sets High and `floor=yes` for any change under `.github/**`, `.mng/**`, `CODEOWNERS` at the root or in `docs/`, any `.gitattributes`, every file the rules resolve to, and any submodule, symlink or mode change. No config removes it. Configured floors (`risk.floors`, Medium by default) mark critical areas. A binary outside `risk.assets` leaves the pull request unrated; a count that does not parse means High.
- **Ratings never walk down.** The level is the highest of the model's level, every floor, Medium for a router `risky`, High for an open or carried confirmed High or Critical bug, the marker's highest, the highest level a person's edit anywhere in the marker comment's edit history names, and the held level (the highest level on any app status for the pull request, `error` included). The held level and the app history count the statuses and rating reviews of the current app and of the apps in `identity.previous`, never the job token's, so an app switch cannot reset them; the nonce, the grant checks and every write stay the current app's. A High stays High until the pull request merges or closes. The app keeps a marker comment with the highest level and the rated heads (head, tree, merge base, rules digest and level), trusted only while the app is its last editor and rebuilt from the app's own statuses otherwise. A head with the tree, base and rules of a rated head takes that level in place of the model's; it never stands in for a rating the engine could not give. A bug thread raises only when validation confirmed its finding (`confirmed` in its marker), and a resolved one counts while a run answered it without closing it, or while the current app's newest answer in it carries `unsettled` (the app could not reopen the thread after that answer, so the resolution GitHub shows may predate it), read from the whole thread when the latest comments do not show that answer. A writer who resolves a bug thread after the run's first thread read is treated like any writer resolving it: step 5 reads the threads again and no longer counts it.
- **Revoke first, grant last.** Every writer of the status runs in one job-level concurrency group per pull request. A publish first writes `error` with the higher of the held level and the level it will publish and reads it back, then posts, checks its nonce is still the newest status, updates the marker from its current trusted text, checks its nonce again, sets the label, re-reads that the head, the merge base, its nonce and the marker are unchanged and that the pull request is still into the default branch, that below High no confirmed High or Critical bug thread is open again, and that no head of the pull request holds a higher level, and writes the grant as its last write. It then reads the statuses again: a grant whose answer was lost stands when it is the newest status, and a grant it cannot confirm, or one a higher level landed just before, gets step 1's `error` again; when that write is refused too, the job fails so the cleanup step writes it. A run that finds another run's nonce newest changes neither the status nor the label, and it checks before the marker update and before the label step, so it does not change the marker either. Step 1 writes its `error` once, and the marker rewrite adds no second status, so nothing in step 1 can take back a nonce a newer run replaced. Later writes with the same nonce are the grant, after step 5's nonce check with one request open between that read and the write, and the revocations below, which write only `error`. A run that is not rated checks its nonce before it removes the label too. A cleanup writes that `error` only while its nonce is the newest status, so it never revokes a newer run's status it can see. When the statuses cannot be read it writes anyway: the `error` never grants and carries step 1's level, so no held level drops, and it revokes this run's own grant if that still stands; a newer run's grant it replaces is lost until the next run. A failure or cancel after step 1 leaves `error` at that level. A failed read or write before step 1 fails the job, so the merge tool sees a run that did not finish. A 404 on a head's statuses is such a failure, since GitHub answers it for a commit the token cannot read too, and so is a commit or force push the timeline lists without its commit, a timeline item GitHub lists as a null node (it may be such a head), and a timeline or status list past 2,000 entries (20 pages of 100). Every other GitHub list the rating, the holds and the sweep read (review threads, a thread's comments, conversation comments and reviews) fails the same way on a node GitHub lists as `null`, since that node may be the answer or review that holds a level; such a read counts its threads open, leaves the run unrated or fails the sweep's pull request, as a failed read does. A comment's edit history is the exception: it keeps a null edit and counts it as High (see the consequences). The old head stays in the timeline, so every later held read fails the same way: that pull request stays unrated for good and goes to the owner. Skipping the head instead could lose the only High it holds. While a run rates, every failed publish fails the job, also one that failed before step 1, whose rules did not load or whose `MNG Review` status GitHub refused; a run that writes nothing by design still passes. A timeline that cannot say who set a label changes no label and writes no grant. A label write that fails writes no grant either, but can leave a partial change (the old level's label removed, the new one not added) until the next run.
- **Who counts.** One rule, the engine's reply rule, decides whose comments hold a pull request or start work: a person, not posted through an app and not a bot the repository owns, with write access by collaborator role. `author_association` decides nothing. Commands keep the owner gate on top, and a refused command from such a person gets a denial answer. A `review` command rates a head at most `risk.reviews_per_head` times.
- **Answers name what they answered.** Each app answer ends with its one marker, which lists the comments it handled with their ids, edit times and the first 16 hex characters of the body digest: the `reply` marker of a converse reply, the `summary` marker of a review, and a new `answer` marker on denial and cap replies. The merge tool treats a comment as answered only when an answer names its current version, so the entry form is a contract between this repository and the merge tool (`docs/spec.md`, Answer entries). Refused commands get their answer from a `deny` job outside the group, since it writes no status. A review or rating names only the commands whose current version is from before its review step started, which the review job records in the outcome file, and from before its run was created, which it reads from GitHub and records in the entry (`created`); a command created or edited in that second or later is left for a later run, since GitHub's times are whole seconds. So a command and the run created for it in the same second never count as answered by that run: the command holds until a later rating run names it or it is posted again, and the merge tool tells the owner so (Rollout requirements). Every reader applies the merge tool's run rule to `review` and `run` entries (`created` later than the command's edit time), so a run queued before a command and started after it never counts as its answer, and the next qualifying run names it. A resolved thread that a dispatched reply answers without closing it (a `needs-owner` or `still-found` answer, for example) is reopened on GitHub before the answer, so the next thread read, the sweep's included, counts it again; when it cannot be reopened, no answer is posted. GitHub gives no resolution time, so that thread and every thread a run sends to the owner is reopened again after the answer: only a resolution made after it then clears the wait. Such an answer is posted with `unsettled` in its reply marker and settled by an edit that drops the flag once that second reopen lands. While the rating is on, a publish that leaves an answer unsettled fails its job, so the failed-run hold applies; without the rating it logs the count and passes, and the wait and the flag stay. While the current app's newest answer in a thread is unsettled, every reader counts the thread as open (the thread raise, step 5's thread read, and the bug counts of a full publish, reply-only publishing and the sweep, which share one rule) and no path clears its wait, the sweep's included. When a resolved bug thread's latest comments do not show its newest app answer, each reader reads the whole thread, and a failed read counts it open. Every later publish tries to reopen the thread and settle the answer, in every thread an owned identity started (after an app switch the current app answers in the previous app's threads) but not in a thread the same run answered, whose own answer decided it; only the current app's newest answer is settled, and only a resolution after that clears the wait. A failed second reopen or settle edit fails the job, so the run hold applies. When the thread read after the answers fails, the run clears no wait. A resolved bug thread whose newest answer is non-closing is not counted for that alone: GitHub gives no resolution time, so that rule would keep counting a bug a writer resolved after a successful reopen.
- **Only the current app answers.** An entry counts only in a marker the app's current identity wrote and no one else edited. Previous identities still own their threads and summaries, but their answers name nothing, so after an app switch the comments the old app answered hold again until the new one answers. That only holds more; a `run <agent>` command answered by the old app goes to the owner. A 404 on a commenter's role means no collaborator, so the comment is not acted on; any other failed role read fails the decide job.
- **An edit now starts a run.** The review workflows listen to `issue_comment` `created` and `edited`, and every per-pull-request writer is named `mng-review-risk-<number>`, so the merge tool can see a writer in flight. This amends ADR 0009, which said an edit starts nothing: an edited conversation comment now starts a named run, and an edited command gets a denial ("the comment changed; post a new command") instead of running. Review events reach the default-branch workflow through a bridge that holds no secret.
- **The sweep raises and dispatches per pull request.** `status-sweep.yml` lists the open pull requests (`risk-pulls`), and a matrix job per pull request (`risk-sweep`) runs in that pull request's group: it raises the status to High for a confirmed High or Critical bug thread, then dispatches at most one run of the review workflow. It reads the runs it counts by fixed job names (`MNG Review rating`, `MNG Review converse`, `MNG Review decide …`), so a run is told apart by its job names, not by its title. A list the sweep cannot hand out whole (past 2,000 entries, or more than the 256 jobs of one matrix) fails it, since a pull request left out would keep a grant its thread should have raised, and so do default branch rules that do not load while the app settings would rate. A `review` dispatch first meets the gate the dispatched review job applies (skip labels, skipped authors and targets), so a skipped pull request spends no dispatch. A failed decide job whose group job was skipped allows one more dispatch of the same comment version; a refused or failed group job blocks it at once. Only writers' review bodies and threads hold, and only the newest of them counts, since a rating after it is after every older one; the dispatch is keyed by it. The runs are listed from the oldest reply that may hold or that newest review hold, or the head's arrival, so a long-open pull request in a busy repository stays under the runs search's 1,000 results. The run limit counts the sweep's dispatches on the head from its own read since the head's arrival, so a new comment never starts a fresh budget on the same head. Only a decide job named with the sweep's source (`MNG Review decide sweep …`) carries a key, so a dispatch from the bridge or anything else never counts toward the limit or the repeat rule. That read can itself reach the runs search's 1,000 results on a long-lived head with many dispatches; the pass then fails closed and dispatches nothing more on that head. A committer date is set by whoever made the commit, so it counts only below the time of a force push that brought the head; a head no force push brought lists its runs from the pull request's creation, and a future committer date cannot hide earlier dispatches from the run limit. Without a dispatch workflow the thread raise still runs, and a pass that needed a dispatch fails.
- **Pure parts live in `packages/domain`:** the `risk` config schema and preset, the description schema with its parser and formatter, the grant and held-level rules, the built-in floor, the floor diff parser, the combine rule, the run-kind table, the acted-on role table and bot exclusion, the answer entry schema, the digests, and one fixture table of command grammar, digest and author cases that the engine and the merge tool both run.

## Consequences

- `risk.enabled` is off by default; nothing changes for a repository that does not turn it on.
- A change to `.github/`, `.mng/`, ownership or the rubric always goes to the owner, and so does every later head of that pull request once it was rated High.
- A model fooled by the change can at worst move a change outside the floors between Low and Medium, or fail to raise one to High. The bench measures how often with injection twins; nothing guarantees it.
- The merge tool still has a window of a few seconds between its final read and the merge call. Closing it needs the merge to run inside the per-pull-request group as an app job with contents write.
- GitHub has no conditional write for a comment or a status. Until every writer runs in the per-pull-request group (the workflows pull request), two short windows remain: a marker update can overwrite another run's entry between its read and its write (that run's grant check then sees the changed marker and leaves it unrated), and a cleanup can revoke a status a newer run wrote between the cleanup's read and its write (an `error`, which never grants). A grant that cannot be read back is revoked, so a failed read costs that rating.
- A person's edit to the marker can raise: when any valid marker form in its text names a higher level (the highest across every form, not only the last), the level counts. Every full run reads the comment's whole edit history (`userContentEdits`, every page by cursor, up to 5 pages of 100, with each edit's id, editor, time and the whole text it left; an app's own edits show as the app) before its step 1, and the highest level any edit by someone other than the current app names counts toward its level and its step-1 `error`; a person's text GitHub does not give, and an edit GitHub lists as a null node, count as High. Such runs rate High, which never merges automatically. Once a run has rated High, any null edit, not only a null original, holds that pull request at High for good through the held level, since ratings never walk down; the marker writes that later push a null edit out of the 99 newest do not lower it. GitHub keeps that text after an app write overwrites it, so an edit a marker write overwrote is carried by the next full run, whatever happened to the write: a rewrite of an edited marker or an update whose answer was lost, a failed or cancelled run after it, or a run that wrote nothing more. A history that cannot be read, or a comment without a node id to read it by, leaves the run unrated at the held level, without raising it. GitHub keeps the original and the 99 newest edits, so an edit drops out only after 99 later ones, and every full run before that carried it. An edit that lands between a marker write's read and the write is overwritten, and the per-pull-request group does not prevent it, since it serializes runs, not people. The rewrite of an edited marker after step 1 rewrites only when the comment still has the text step 1 read, and writes no second status; a later edit waits for the next run. The update after step 1 reads the history before and after its write and takes as the edits since the first read those the second lists by an id the first did not, which still sees the run's own update at GitHub's 100-edit retention, whatever GitHub's order or edit times. When anyone but the app edited the comment in between, the run stays unrated. The history read before the write also stops a grant below the highest level it names, since GitHub can list an edit only after the run's start read the history. When the history after the write does not list the run's own update yet, it is read again three times, two seconds apart, before the run stays unrated. A person can instead set a risk label higher than the status: the label does not raise the status or stop the grant, but the merge tool refuses a pull request whose risk label is higher than its status level. When the history cannot be read in full (a page fails, the count changes between pages, or it runs past the bound), still does not show the run's own update, lists more null nodes after the write than before it, or counts more edits since the read than it lists, the run stays unrated too.
- The label step reads the labels, the timeline, the labels again and the timeline again just before its writes, and changes no label when the labels or their timeline events changed between those reads. A person who removes the bot's label and adds the same name back before the second timeline read therefore keeps it as theirs. GitHub has no conditional label delete, so a change between that second read and the writes, one request, can still be taken for the bot's. That window is longer than one request when GitHub lists a label event in the timeline only some time after the change: a change whose event the second timeline read does not list yet looks like no change.
- After an app switch, the previous app's statuses still hold their levels and its ratings still count as history, but its marker is not the current app's. A pull request it rated therefore has app history without a trusted marker and stays unrated until the owner merges it.
- A new pull request with the same change starts with no history. Floors and threads still apply; only the model's level can come out lower.
- The held level is read in the publish job, after the review job's model calls, not before them as the design has it. A failed held read therefore costs the run's model calls, and the next run pays them again. A probe in the review job before the model call was left out; it would read the timeline and statuses twice per run, and the read in publish still decides.
- A thread run (`run <agent>`, reply-only, converse) writes step 1 after its posts, since it can only raise to High, so a failed held read there comes after its posts. When its posts fail part way, its thread raise still runs, counting the threads it answered without closing them, and the job fails.
- A `failed` outcome (the review leg failed) publishes nothing, so a failed `review` rerun over a granted head leaves the old grant on it, where the design's run-kind table writes `error`. The review job exits 1, so the run concludes `failure` and the merge tool's run hold keeps the head unmergeable until a newer app status.
- The cleanup is its own mode, `risk-cleanup`, so a failed or cancelled publish step still gets step 1's `error` written again. It needs the publish step's `risk-description` output; without it the cleanup only removes the label.

## Rollout requirements

Before a repository turns the rating on, its workflows and the merge tool must meet these; the code cannot check them.

- Every writer of `MNG Review risk`, the cleanup included, runs in the job-level group `mng-review-risk-<number>`.
- The workflow runs the cleanup with the publish step's `risk-description` output after any publish failure or cancel.
- The merge tool refuses a pull request when any of its risk labels is higher than the status level, so a person's higher label blocks the merge without raising the status.
- The merge tool's readiness check tells the owner to post a `review` or `run <agent>` command again when it is unanswered and older than the newest finished rating run for the head: a run created in the same second as the command never counts as its answer.
- The review workflow names its jobs as the sweep reads them (`docs/spec.md`, Dispatches and job names), and no `run <agent>` job is named `MNG Review rating`. Its decide job repeats the dispatch's `source`, and only the sweep passes `sweep`: a bridge or other dispatch passes another source or none, so its run never carries a key the sweep counts.
- The `risk-sweep` matrix job runs `risk-cleanup` with its step's `risk-description` output after a failure or cancel, since a thread raise whose grant may still stand fails the job.
- The `risk-sweep` job fetches the default branch tip and the pull request's head as git objects; the thread raise reads their merge base and leaves the pull request unrated without them.
- The push run (`pull_request_target`) comes from the same workflow file as `MNG_REVIEW_DISPATCH_WORKFLOW`, since the sweep counts only that file's runs. Its runs must list the pull request in `pull_requests[]`: the spec fixture follows GitHub's documented `workflow-run` schema, not a captured run, so check one real push run's payload before turning the rating on.
- The `risk-sweep` matrix job is named `MNG Review risk-sweep <number>`, in the `status-sweep.yml` run titled `mng-review-risk-sweep`. It is not a `mng-review-risk-<number>` run, and a held read that fails before step 1 writes no status, so the merge tool reads that run's jobs and holds a pull request whose newest `risk-sweep` job for its number ended in anything but `success` or `skipped`, until a newer app status for that number.
- The merge tool holds a pull request while the newest run of a status writer for its head failed or is in flight. A `success` can stay the newest status when both the read-back and the `error` over it fail, and the cleanup cannot revoke it when the description output is lost or the cleanup's own write fails.

## Rejected

- A label as the permission: anyone with write access sets labels, and the job token can too.
- The job token as the writer: a same-repository pull request can add a workflow that writes statuses and labels as `github-actions[bot]`.
- Lowering a rating on a later head, or an override that lowers one: the owner merges by hand instead.
- `author_association` for who counts: a private organization member shows as `CONTRIBUTOR`, and it does not see custom roles (ADR 0009).
