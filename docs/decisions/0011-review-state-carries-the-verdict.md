# ADR 0011: The review state carries the verdict

**Status:** Proposed
**Date:** 2026-11-23

## Context

Since ADR 0010 each publishing run writes one review whose body is the summary, always as `COMMENT`. A reader still has to open the body to learn whether the bot found something blocking, and GitHub's review list and filters cannot tell a clean pull request from one with open bugs. Other review bots post `APPROVE` and `REQUEST_CHANGES`. Approving carries a risk a comment does not: where a branch rule requires approving reviews, a bot's approval may count toward it, and the reviewed change is text that can talk a model into finding nothing. The job token (`github-actions[bot]`) cannot approve by default: GitHub answers 422 "GitHub Actions is not permitted to approve pull requests." unless a repository setting allows it. Its `REQUEST_CHANGES` works and counts in the pull request's review decision. An app with pull requests write can approve, request changes and dismiss its own reviews; its reviews have author association `NONE` and do not enter the review decision today. On GitHub a later `COMMENT` review does not replace an author's earlier `APPROVED` or `CHANGES_REQUESTED`, and editing a review's body does not move it to a newer commit. GitHub refuses a review state from the pull request's author.

## Decision

- A run changes the bot's review state only when it has evidence for the new state; otherwise it keeps the state. The pure `getReviewDecision` in `packages/github/src/modules/publish/domain` decides from the evidence each run carries and from whether an owned change request stands:
  - The current head is the pull request's head as the summary write reads it right before the review write, again before the cleanup and once more before the dismissals, never the head the run reviewed; a push or command run whose earlier head check found another head stays off it too. A run that reviewed another head, or could not read it, keeps the state, and change requests are dismissed only while the last read still shows the reviewed head (the dismissal API takes no expected head, so this narrows the window without closing it). When the write's first read no longer shows the reviewed head, the run counts as partial: its marker keeps the previous head and flags, so a stale run never moves the marker back over a newer head.
  - `REQUEST_CHANGES` for a push or command run on the current head that leaves a confirmed bug thread at or above the severity floor open, new or carried over (bugs without a thread count too), or a thread waiting for the owner, and for a reply-only run on the current head and the head of the last full review whose standing verdict is `needs fixes` or `needs owner`, so an approval never stands next to a reopened bug.
  - `APPROVE` only for a push or a command that named no agent, finished on the current head with the verdict `ready`, and covered the whole change (`getCoverageGaps` finds no gap): the plan ran the main reviewer (a quick run skips it, so it never approves), no changed file was skipped as too large or binary, the token budget stopped no finder, unit or validation, every planned run reported `ok` with no unit that failed or timed out, the main reviewer received every changed file in its scope whole (`unread` in the agent report counts the ones it did not: a file counts as read only when its first message showed the whole diff, every part of its diff came back from `diff`, or, for a file that deletes no line, `read_file` at the head showed every added line (a read of the head never shows what a deletion removed, so a file with a deletion counts as read only through its diff); a partial read, `blame`, one diff part or a finding on the file never counts, nor an output a failed continuation sent), the run kept no finding (no unverified finding, nothing below the floor, no nit), and publishing's own second read of the threads, after its answers, succeeded and finds no open unverified or nit thread of the bot (that read decides which threads are open: one this run closed counts closed only while the bot's closing reply is still its latest comment; a failed read keeps the first for the run's work, but approves and clears nothing), and the write's head read shows the pull request open and not a draft (a draft or closed one keeps the state). Unverified findings and nits alone therefore leave a `COMMENT`.
  - `COMMENT` for such a run that finished `ready` with every planned run and unit finished but did not cover the change (findings that never block, skipped files, unread files), or with approval turned off.
  - A reply-only run never approves. On the current head and the head of the last full review, with the standing verdict `ready`, a last full review whose runs all finished (the marker's `failed` flag) and a second read of the threads after its answers that succeeded, it comments; anything else keeps the state.
  - A clearing run needs every planned run and unit finished: a missing report, a failed agent, an agent `error` (such as a deep unit that failed beside units that answered) or an endpoint error keeps the state, whatever the verdict. Non-blocking gaps (nits, unverified findings, skipped or unread files) still let a run clear a change request with `COMMENT`; they only block approval.
  - A run whose head is not the current head or could not be read again (push runs read it too), a command that named one agent or a run that did not finish and found nothing blocking, a run with a failed run or unit, a run whose list reads left a null node out (ADR 0012), and an offline run keep the state: they edit the bot's newest review in whatever state it is, except an approval or change request on another commit or, for a run whose head is not the current one, on the current head, and, for a run whose list reads left a null node out, an approval of the current identity, over which it posts a `COMMENT` instead; when they must post (new threads, or nothing to edit) they post `COMMENT`, which on GitHub leaves an earlier approval or change request standing. A run whose head is not the current one records its marker and never dismisses, edits or hides an approval or change request on the current head; a write that could not read the current head hides none.
  - A change request needs evidence on the current head. The only kept run that posts `REQUEST_CHANGES` is a reply-only run on the current head, off the last full review's head, that finds something blocking while an owned identity's standing verdict is a change request; an identity's standing verdict is its newest approval or change request, dismissed ones aside, so one a later approval superseded is never revived.
  - On a pull request the bot's identity opened, every state is `COMMENT`; the offline path reads the pull request for that too.
- The review body opens with one line that names the state in words that match it, `**Approved.**`, `**Changes requested.**` or `**Comment.**`, written for the state the review lands in (an edit keeps the edited review's state). Every state but a fresh approval follows it with one sentence on why the bot did not approve, with the counts the engine recorded, for example "Not approved: 3 of 41 changed files were too large to review.", "Not approved: the review stopped at its token budget before reading every changed file." or "Not approved: only findings that do not block remain (2: unverified, below the severity floor, or nits), and the bot approves only a change it has nothing left to flag." When several reasons apply, the sentence names each coverage gap and each restriction (a pull request the bot opened, a draft or closed one, `verdict.mode: preview`, token mode), joined with semicolons. The findings count adds the open unverified and nit threads no kept finding matches by fingerprint; the unread count is the most any one reviewer run left unread, since the report carries counts and not paths. The sentence is fixed text and numbers, never model output. A run whose list reads left a null node out gives "Not approved: a list GitHub returned was incomplete (reviews), so this run did not approve, lift a change request or clear a wait." first, naming each list that left an entry out (review threads, thread comments, conversation comments, reviews), then any other reason, joined with a semicolon. A run whose list reads left a null node out never raises approval: it does not approve, write a `success` status, lift a change request or clear a wait. It may always lower approval: it still dismisses the bot's own stale and replaced approvals and the review a push outlived, dismisses the current identity's approval of the head it reviewed when its verdict blocks (`needs fixes` or `needs owner`), since its `COMMENT` would leave that approval standing, and turns a `success` status into `pending` when the head's status can be read, also when its summary write fails (a reply-only run writes the status its standing gives, a full run `error`); when that read fails it writes no status, warns in the job log and sets `statusUnread` in the run result. An approval that is itself the node a read left out cannot be withdrawn, since the run cannot see it; that is no worse than before. When any list read of the run left a node out, that node may be a newer summary its marker should build on or something its verdict missed, so the run still writes its summary, with this run's findings, its unthreaded bugs and every wait it saw, but marks its marker unfinished and failed; when the summary write's own read left it out, the run posts that summary as a new review instead of editing one, so it is the newest. Until a full run that finishes with complete reads replaces that marker, no run and no sweep reads it as `ready`, writes `success` or lifts a change request on it, and a reply-only run on it, also one whose summary write fails, and a one-agent run or a full run that does not finish, which keep that marker, write a status that does not block only over no status or a `success`, and nothing when they cannot read the head's status. A marker's run and manual run counts, as every run and every cap reads them, are the most any listed summary holds, reviews and sticky comments alike, hidden ones included, so they never fall below what the summaries a read lists hold. A write that cannot see the summary with the higher count stores a lower one, and a run spent then is not added back, so the run caps can undercount until that summary is listed again; the caps bound cost, not approval. Each write replaces the previous headline.
- `verdict.mode` in `.mng/review.yml` turns approval off: `approve` (the default) lets a covered run approve, `preview` posts `COMMENT` where it would approve. The key was already in the schema and read by nothing; it is validated there.
- In token mode the bot never approves: whether the token's identity is `github-actions` decides, never a retry after the 422.
- An approval or change request stands for its commit. A run never edits one whose commit is not the current head; it posts a new review. `COMMENT` bodies are still edited in place (ADR 0010). Writers read each review's commit through GraphQL, which needs contents read; the reservation reads no commit and edits only the marker.
- A change request must not outlive its evidence. Only a write that clears dismisses (`PUT /pulls/{n}/reviews/{id}/dismissals`) the owned reviews still in `CHANGES_REQUESTED`, with one fixed line as the reason: an approval (the current identity's own change request then stands replaced and is kept), a full finished run `ready` on the current head with every run finished, or a clearing reply-only run.
- An approval must not outlive its head. After every write that does not leave the current identity's approval on the current head, offline ones included, the bot dismisses the owned approvals on another commit than the current head (none of the current identity's when the head could not be read); after every write by a run on the current head, the approvals of other owned identities, which it replaces. A run whose head is not the current one dismisses other identities' approvals only on another commit than the current head, and a write that could not read the current head dismisses no approval. When the read after the write shows another head than the commit of the review the write left, a push landed between the two reads, and that review is dismissed when it approves, or when it requests changes and this write posted it, since it does not stand for the current head; a change request the write only edited keeps its evidence and stays until a clearing write. A review is dismissed once, by this rule, even when it is also an approval on another commit.
- The reply schedule (`review-converse.yml`) dismisses the current identity's change requests when no open bug thread, no bug without a thread in the newest summary marker, whatever head it is on (after a push the new head may never be reviewed, so only a later marker that no longer lists them clears them), and nothing waiting remain, whether or not the last run finished, with the same reason; `status-sweep.yml` writes statuses only. With the marker on another head, which an unfinished full run leaves, it dismisses only those on a known commit other than the pull request's head. Its read-only `find` job lists a pull request only when such a dismissal is due, and a `lift` job judges each listed pull request again inside its publish group (`mng-review-publish-<pull request>`, ADR 0009), after the schedule's publish legs, so no publishing run writes threads, a summary or a status between that judgment and the dismissal. The lift job reads the pull request, then the reviews before the threads, and dismisses only reviews from that read, so a change request posted while it read is never dismissed. It dismisses nothing while a list read left a node out or the newest summary is one an incomplete write left unfinished and failed (ADR 0012), and right before dismissing it reads the pull request's head again and dismisses nothing when the head moved (the dismissal API takes no expected head, so this narrows the window without closing it). A read that fails fails the lift job and dismisses nothing. It writes no status: the status sweep turns the status green in the same schedule run, and a `success` the sweep writes after a late writer's `failure` is repaired by the next sweep or the next status a run writes. That needs pull requests write in the lift job, and pull requests read in the sweep. Remaining limit: a person, not a run that writes in the group, who reopens a thread inside the lock, after the lift job's judgment and before its dismissal, can still have the change request dismissed while a bug is open. The next status sweep repairs the status; nothing restores the change request, and the next run that finds the bug posts a new one: a push or command run on the current head, or a reply-only run on the current head when that head is also the head of the last full review. None posts one while its list reads left a node out, or on a pull request the bot's identity opened.
- A dismissal GitHub refuses is counted in the job log and the result file's `publish` field (and in the lift job's line) and left for the next run. When the write's own review was dismissed because a push landed right after it, the result's `outlived` is `true`: `event` is the state it was written in, which no longer stands. Another owned identity's approval on the current head is dismissed with a reason saying the current identity's review replaces it; an approval on another commit with one that names the current head it does not stand for, never a claim that the current head has no approval.
- Unchanged: the replies in threads, thread resolution, the `needs-owner` label, the `MNG Review` commit status and the per-agent check runs.

## Consequences

- A clean, covered push by the app shows as an approval; a push that brings a bug back posts a new change request, and the next write dismisses the approval on the older head.
- In token mode a change request from `github-actions[bot]` blocks merging where a branch rule requires that no review requests changes, until a clearing run, or the reply schedule's lift job after the last thread is resolved, dismisses it. A later `COMMENT` never lifts it.
- An approval is evidence only of what the model read. A forged outcome file, or a change that talks the model into an empty outcome, yields an approval exactly where it already yields the `success` status; preview mode and the status gate do not change that.
- The app's reviews do not count toward the review decision today (author association `NONE`), so its approval satisfies no rule that requires approving reviews; they would count if the app's access to the repository changed, for example by making it a collaborator. A repository that does not want that sets `verdict.mode: preview`.
- The commit status and the review state say the same thing in two places; the status stays the gate a branch rule should require, since the sweep refreshes it when someone resolves a thread by hand and the review state changes only when a run or the reply schedule's lift job writes.
- The reply schedule's lift job holds pull requests write; the sweep's token needs pull requests read only.
- The default: all three council reviewers recommended `preview` as the default, since a forged or model-fooled empty outcome would approve, and approvals would start to count toward the review decision if the app's access changed. The owner kept `approve`, because approval now requires a finished full run on the current head that covered the whole change.
- `verdict.never_approve` and `verdict.blocking_severity` stay in the schema and are still read by nothing.
