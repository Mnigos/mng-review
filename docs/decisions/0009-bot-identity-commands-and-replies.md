# ADR 0009: The bot may post as a GitHub App, a mention of it starts a review, and it answers replies in its threads

**Status:** Proposed; ADR 0010 moves the sticky summary into the bot's review
**Date:** 2026-11-20

## Context

Publish mode (ADR 0007) posts with the job token, as `github-actions[bot]`. That name is shared with every other workflow in the repository, events made with the job token start no workflows, and a handle a person can mention needs an account of its own. A GitHub App gives the bot its own name, but its key can write wherever the app is installed, and a repository that switches already has threads and a summary written by `github-actions`. Commands let a person start a review from a pull request comment. They act on text other people write and can spend the endpoint's quota, `issue_comment` workflows run from the default branch, and comments the app writes start workflows too. An author's reply in one of the bot's threads ("fixed", "intentional because …") is text other people write as well, and a wrong answer to it closes a thread or blocks a pull request.

## Decision

- The app is optional. With `app-slug` and the secrets `app-client-id` and `app-private-key` set, every write comes from the app. Without them nothing changes. Setting only some of the three fails the job before any write.
- Only the jobs that write reference the two secrets: `publish` in `review-publish.yml` and `sweep` in `status-sweep.yml`. The review job, which calls the model, never holds the key. A writing job mints an installation token with `actions/create-github-app-token`, pinned by commit, after its checkouts. The token covers the calling repository only (no `owner`, no `repositories`) and the permissions the job writes with: pull requests, checks and statuses write for publishing, statuses write and pull requests read for the sweep. The action revokes it when the job ends. A failed mint fails the job, and nothing falls back to the job token.
- Every job that runs the entry gets the slug as `MNG_REVIEW_APP_SLUG`. A writing step also gets the app token and the slug the token was minted for, and exits 2 before any request when that slug differs from the configured one without regard to case, when the slug is not a valid app slug, or when a token of the other mode is set. In app mode the entry never receives the job token, which then only checks out and fetches. The prepare step reads with the job token and needs the slug only to know which bot wrote the summary and the threads.
- The owned identities are the token's identity and the slugs in `identity.previous` of `.mng/review.yml`, read where the rules are read: the base commit for a push, the default branch for the sweep, so a pull request cannot widen them for itself. The preset is `[github-actions]`. A repository that leaves the app sets it to the app's slug; `[]` drops the trust once the pull requests opened before a switch are closed.
- A comment is the bot's when its author is a `Bot` whose login is owned, compared without case, and its editor is `null` or that same bot. An edit by another bot, even an owned one, ends the ownership.
- The bot creates as its current identity, edits and deletes only what that identity wrote, and replies in a thread of any owned identity. A reply of any owned identity closes a thread for the bot's counts, so the app's "no longer found" reply closes a `github-actions` thread. The only thing it does to another identity's comment is hide or delete a superseded summary.
- The summary is the current identity's oldest summary when it has one; otherwise the oldest visible summary of another owned identity is the prior state. A write then creates the current identity's summary over that marker, so the run count and last head carry over, and hides the old summary as outdated. When GitHub refuses to hide it (a 4xx other than a rate limit, or GraphQL errors of type `FORBIDDEN`, `NOT_FOUND` or `UNPROCESSABLE`), the bot deletes it, and a 404 on that delete counts as deleted; when hiding gets no answer, a 5xx or a rate limit, which may still pass later, or GitHub refuses the delete too, it stays and the result file reports `kept`. An offline run moves the summary the same way, with the marker set to unfinished, so the sweep never reads the old summary's finished run for a newer head. Summaries of the current identity that two runs created at once are deleted on every write except the oldest; a 404 on that delete counts as done. While more than one such summary is visible, the sweep leaves the status as it is. Every later write tries the cleanup again while such a summary is visible. A hidden summary is never read.
- Two runs that create the summary at once leave one: after a create the bot reads again, and when an older summary of its identity exists it renders over that one's marker, edits it and deletes its own new comment. When that edit fails, the bot deletes its own new comment and the write fails, so the run reports `failed` and the next run starts from one summary. A create with no answer or a 5xx is followed by a read before anything else: the newest summary of the current identity that was not in the read before the create and has this run's body is taken as this run's own create, and the oldest summary of the identity is then kept or edited the same way; with none the write fails and the next run tries again.
- The status the sweep refreshes is the newest `MNG Review` status set by a `Bot` with an owned REST login (`<slug>[bot]`). Check runs carry no ownership check: each run creates them with its token and never updates them.
- The job token of the publish job keeps write in app mode, because job permissions are static text and token mode needs them. The job that holds it also holds the app key, which can do more, so the token adds no reach.
- The user login that matches the app's slug is reserved, for example with an empty organization of that name, so a mention of the handle can never reach someone else's account; a mention of an organization notifies nobody. The `mng-review` login is reserved this way.

### Commands

- A command is a line of a new pull request comment that holds only `@<handle> review`, `@<handle> review deep`, `@<handle> review quick` or `@<handle> run <agent>`, after up to three leading spaces, with words separated by spaces or tabs. The handle is compared without case; `@<handle>[bot]`, `@<handle>:` and a longer login are not the handle. The verbs are lower case. `<agent>` matches `[A-Za-z0-9][\w.-]{0,63}`, so `run review` names an agent called `review`, and bare `review` is always a full review. A mention with no verb, an unknown verb or extra words is no command. The first command line wins.
- Lines that never count: text in an HTML comment (an unclosed one runs to the end), lines in a fenced code block, lines indented by four spaces or a tab, a quoted line and every non-blank line after it up to the next blank line. GitHub's quote reply leaves that blank line, so a command typed under a quote still counts, and a mention that runs on lazily from a quote does not. The parser follows GitHub's Markdown for these rules but is not a full renderer, so a rare construct can render differently from how the parser reads it; the authorization check, not the parser, keeps anyone else from spending the endpoint's quota.
- The handle is a workflow input, never text from a comment or a pull request. In app mode it is `app-slug`, and the reserve job checks the minted token's slug against it before any request. Without the app it is the `handle` input of `review-command.yml`. There is no default: `@mng-review` without the app would mention whatever user account holds that login. Both inputs set is refused; neither set starts no job. The entry checks the handle against the slug pattern before it compares anything and builds no regular expression from it. The login that matches the handle is reserved, as for the app.
- `review-command.yml` runs four jobs. `authorize` holds no secret and a read-only token, and reads the rules from the default branch: the event is `issue_comment` with the action `created`, on a pull request, by a `User` that is not an owned bot's REST login and not posted through an app; the comment holds a command for the handle, reads the same when fetched again, and comes from an admin or a login in `commands.allow` that still has `maintain` or `write`, or a custom role whose base permission is write or admin (a custom role never counts as admin); a named agent is declared; the pull request is open, from this repository, with two full commits; and the owned summaries' `manualRuns` is below `commands.max_runs`. Any GitHub error denies, and a denial passes the job. `reserve` holds the app key and an app token with pull requests write only, since it reads no GraphQL field that names a commit: it reads the pull request again, applies the base commit's gates and the named agent, and counts the manual run in the summary's marker before the endpoint is used, creating a status summary with `finished: false` when none exists. `review` holds the endpoint, the tailnet and a read-only token. `publish` holds the app key, as in `review-publish.yml`. The token that reserved is revoked when its job ends, before the review starts.
- The later jobs take the pull request and both commits from `authorize`'s outputs, never from the event or the outcome file, and the outcome's binding names the trigger (`push` or `command`). A pull request that closed, moved or became a fork skips the run in `reserve` and in the prepare step. `publish` reads the pull request again and posts nothing when it closed or became a fork during the review; a head that moves while the command reviews makes the run partial (ADR 0008). Whether the run named one agent comes from the publish job's own context.
- `reserve` and `publish` run in the group `mng-review-publish-<pull request>` with `cancel-in-progress: false`, the group of `review-publish.yml`'s publish job, so every summary writer on one pull request runs one at a time. Only `reserve`, `review` and `publish` check `github.run_attempt == '1'`: a re-run would carry the first attempt's authorization to whoever starts it, so a failed command is started again with a new comment.
- A mention in a review thread is never a command: `pull_request_review_comment`, `pull_request_review` and pull request edits start no command workflow, and in a thread the bot owns it is a reply. A conversation comment is never a reply.
- Who can spend what: only an admin or an allowed writer reaches the endpoint, at most `commands.max_runs` times per pull request. Anyone else's mention, a quoted mention and a mention that fails the grammar cost one job of seconds with no secret. An edit, the pull request body and review comments start nothing. The bot's own comments start nothing: they are a `Bot`'s, and every fixed text that names the handle puts it in a code span, so they hold no live mention.

### Replies

- Replies are never handled from `pull_request_review_comment`, whose workflow file comes from the pull request's merge ref. They are answered in the push and command runs that are not skipped, and polled on a schedule from the default branch (`review-converse.yml`), so no workflow a pull request can change sits next to the secrets. A push at `limits.max_runs_per_pr` is skipped and its replies wait for the schedule.
- A reply should not wait for the cron. The caller adds a signal on `pull_request_review_comment` that holds no secret and no write token and only waits 15 seconds, and starts its schedule file with `workflow_run` when the signal completes; `workflow_run` runs the default branch's file and the reusable workflows read nothing from the signal's run. The schedule acts only on a successful `pull_request_review_comment` run from this repository and puts every other run in a concurrency group of its own, so a fork's rewritten signal starts nothing and a skipped one cancels no waiting run. A writer's branch that edits the signal runs it with the repository's secrets, as any workflow a writer pushes already can, and can start the schedule more often: that costs runner minutes, the shared API budget and the model again for a reply whose answer did not land, and answers nothing a writer did not ask. The wait lets a resolve that follows the reply land before the sweep reads the threads. A thread resolved with no reply starts nothing (`pull_request_review_thread` is not a workflow trigger), so it waits for the cron, which GitHub can delay or drop.
- The schedule's `find` job holds no secret and a read-only token: with the default branch's rules it lists the open pull requests of this repository, never drafts or forks, where a reply counts, and keeps at most `max-pull-requests` (5), oldest reply first. It reads each pull request's threads first and reads the summaries, the bot's longer threads and the authors' access only where a person's reply is the latest comment, and it takes the waiting list from the same sources as publishing, so a thread that waits for the owner never lists its pull request. A failed list, or a read that failed on every pull request, fails the job. When more wait, the run number shifts the batch, as it shifts the replies inside one pull request, since a reply-only run never advances the run count. Its output, numbers and full commit SHAs it validated, is the matrix of a `review` job (endpoint and tailnet secrets, a read-only token) and a `publish` job (the app key), one pull request at a time. The review leg probes the endpoint and decides on the replies only: no finder, no re-check. Both legs read the pull request again; one that closed, became a draft or a fork, or moved to another head or base since `find` listed it gets nothing, and the leg passes for the next tick to read it again, so an answer never applies an old base's rules or sets a status on a head that now targets another branch. The publish leg applies the decisions with the same checks as a push run's publishing (the author's write access and the reply's digest read again, `needs-owner` only past the limit or the rounds, the waiting list rebuilt from every owned summary and the bot's `needs-owner` answers), updates the waiting list, the verdict line and the status, and posts no thread and no check run; the summary's run count, head, finished flag and unthreaded bugs stay. Such a run ignores the `skip` rules and the run limits, since a reply on a skipped pull request is still the author's question, and counts toward neither.
- What one tick can spend is bounded by `max-pull-requests` times eight conversations, each inside `limits.tokens_per_run`, and only a login with write access can cause one. A tick with nothing waiting runs `find` alone, one short job with no secret.
- The prepare step, which holds the read token and no endpoint, finds the replies before any model call: the latest comment of an open `bug` or `unverified` thread of an owned identity, written by a `User`, not ending with a marker of the bot's form, in a thread that does not wait for the owner. The author must have write access (`admin`, `maintain`, `write`, or a custom role whose base permission is write or admin); a GitHub error means the reply does not count. At most eight threads per run, a different batch each run when there are more, rotated like the re-check. Each reply is cut to 4,000 characters, and the bot's earlier `disputed` answers in the thread are counted from owned, unedited comments only, so a pasted marker counts for nothing.
- The classification and the re-check run in the review job, on its token ledger, after the re-check of unanswered threads; a thread with a reply was never a re-check candidate. The outcome file carries each decision bound to its thread id, the thread's fingerprint, the `databaseId` of the comment it answers and a SHA-256 digest of that comment's text as the prepare step read it, never the reply's text. A reply left `seen` by a failure of the model, git or the budget is not in the file, so the next run tries it again. A run that reviews nothing decides nothing.
- The publish job reads the threads again and applies a decision only when that thread is still the bot's, open, has the same fingerprint, does not wait for the owner, and its latest comment is still the one the decision names, by a `User`, with the same digest. Otherwise someone answered or edited the reply meanwhile, the decision is dropped and the next run reads the thread again. Right before each answer it reads that thread once more and posts only when the decided reply is still the latest comment with the same digest. GitHub's reply mutation takes no precondition, so an edit or a comment that lands between that read and the post can still be answered; the window is the time between two requests. Two overlapping runs answer a reply once: the second finds the bot's answer as the latest comment. Publishing then looks up each remaining reply author's access once more (one lookup per login) and drops a decision whose author has no write access or whose lookup fails, so a review job cannot get a reader's reply answered by naming its comment, and an author who lost access since the prepare step gets no answer. Publishing also drops an `accepted` decision on a finding past the limit an `intentional` reply cannot pass (a `critical` finding, a file under `risk_paths`, a severity above `disputes.accept_intentional_up_to`): the severity comes from the bot's marker, the rules from the base commit, and the changed files and renames from its own git read between the bound base and head commits, never from the outcome file, which the review job shapes. A failed git read drops it too.
- The review job runs model code, so publishing also checks the closing decisions with its own git reads at the bound commits. A `resolved` decision stands only when the thread's commit is an ancestor of the bound head and a commit after it touched the finding's file (a rename of the file counts), the gate the engine applies before its re-check; otherwise a forged `resolved` would close a thread on code no one changed. An `accepted` decision carries at least one evidence entry, and publishing checks each entry again with the engine's evidence rules: a repository path, lines that exist at the head (or at the merge base for a file missing at the head) and that the pull request did not add, in no binary, `-diff` or symlinked file. The answer shows only the entries that pass, and with none the decision is dropped. One condition cannot be checked at publish: that the classifier was shown every cited line whole. That one rests on the review job.
- A thread this run closes (`resolved`, `accepted`, or the re-check) is not posted again in the same run when the report still holds its finding: the finding is dismissed. A later run asks whether the finding's code changed since the head the closing answer names, not since the thread's first commit, so a change made before the answer does not repost an accepted finding.
- Each answer ends with a reply marker (`action`, the head, and `reply`: the comment it answers). `resolved` ("no longer found") and `accepted` close the thread for the bot's counts and ask GitHub to resolve it. `accepted` names the checked evidence and the memory candidate in code spans, trusted only once a person merges it into `.mng/MEMORY.md`. `still-found` and `seen` are not rounds: a `fixed` reply the validator does not confirm is a fact about the code, not a disagreement, and an unclear reply asks for `fixed` or `intentional because` with a `path:line`. `disputed` names the failed premise. Every model text is escaped.
- `needs-owner` is one final answer. Publishing accepts it only past the limit an `intentional` reply cannot pass (a `critical` finding, a file under `risk_paths`, a severity above `disputes.accept_intentional_up_to`), checked again from the thread's marker, the rules in force and the change publishing reads from git (when that read fails, only the rounds count), or when its own read of all the thread's comments counts at least `disputes.max_rounds` owned, unedited `disputed` answers; a failed read drops it. So a review job cannot send a thread to the owner on the first reply.
- The thread's node id goes into the summary marker's `needsOwner`, since a later comment in the thread would hide the bot's answer from a read of the latest comment. Publishing and the sweep take the waiting list from every summary of an owned identity, the current one or a previous one, hidden (minimized) ones included: a writer may hide the bot's summary but cannot write one. They also count as waiting every review thread, open or resolved, with an owned, unedited `needs-owner` answer anywhere in it, whoever owns its first comment now, so an edit to that comment does not end the wait: the thread read brings each thread's ten latest comments, and a thread whose first comment an owned bot wrote, edited or not, with more comments than that is read whole, except the bot's own `nit` threads. Publishing adds every such id to the list before clearing and before it builds the next marker. So an answer whose summary write failed, a hidden summary, a resolve by a writer, an edit to the thread's first comment and comments that push the answer out of the latest ten all leave the thread waiting. When the whole read of a thread fails, the sweep leaves the status as it was; publishing counts only the latest ten comments for that run. While the list is not empty the verdict is `needs owner` and the status `failure`, the summary lists the threads, and the pull request carries the `needs-owner` label.
- A thread leaves the list when an admin, or a login in `commands.allow` with write access, resolved it on GitHub (`resolvedBy`, checked with the collaborator role). Who resolved it is read by thread id from the raw thread read, not from the bot's threads only, so a waiting thread whose first comment someone else edited, which is no longer the bot's, is cleared the same way; a writer resolving it still does not clear it. The next run removes the label when the list empties. The status sweep makes the same checks and never edits the summary.
- The label is written with pull requests write, which covers adding a label and creating a missing one; no token asks for issues write.

## Consequences

- Comments, statuses and check runs the app makes start the repository's other workflows, which writes with the job token never did.
- Every job that writes the summary runs in the concurrency group `mng-review-publish-<pull request>` with `cancel-in-progress: false`, so two writers never both read the same marker and record one run instead of two; later workflows that write the summary use the same group.
- A required `MNG Review` check bound to GitHub Actions blocks every pull request once the app sets the status. The check's source must be set to any source before the switch and to the app after it.
- While `github-actions` is in `identity.previous`, another workflow that posts as `github-actions[bot]` can still plant a marker, as ADR 0007 records.
- After `identity.previous: []` on a pull request opened before the switch, the bot posts the old threads' findings again, and an old summary it could not hide stays visible.
- Accepted race: two runs writing one summary while one of their creates gets no answer can count one run twice. That only makes `max_runs_per_pr` stricter.
- A reconciliation that fails after a create fails the run instead of leaving two summaries of the current identity; the next run starts from one.
- GitHub keeps one waiting job per concurrency group, and `reserve` and both publish jobs share `mng-review-publish-<pull request>`, so a newer waiting job cancels an older waiting one. A command's `publish` can be cancelled after its run was counted and the model was paid for, and a command's `reserve` can cancel a waiting push publish, which leaves that head without a status. To recover, re-run the push run's workflow, or post a new command comment.
- A comment posted through an OAuth app with a user token has no `performed_via_github_app` and counts as the user's; no API field tells it apart.
- Two authorized commands, or a command and a push, may review at once; the overlap rules of ADR 0008 cover it.
- A writer resolving a waiting thread, or removing the label, does not clear it. A waiting thread whose first comment someone else edited is cleared like any other, by an admin or an allowed login resolving it.
- Gap: a deleted waiting thread stays in the list, since nothing can resolve it, and the pull request stays `failure` until a person edits the summary marker.
- Gap: a thread that holds the bot's `needs-owner` answer waits whenever no owner's resolve stands on it, so a thread an owner cleared and someone reopened on GitHub needs an owner again, as does one whose resolver later lost admin or left `commands.allow`.
- Gap: an edit by anyone else ends the bot's ownership of a comment. A writer who edits both the summary that lists a waiting thread and the bot's `needs-owner` answer in it, and resolves the thread, clears the gate without an owner. GitHub records the edit (`editor`), and the bot never trusts the edited comments again.
- Gap: when a whole-thread read fails in publishing, an answer beyond the latest ten comments is not added to the marker in that run; the hidden-summary list and the next run still hold it.
- A reply without a push waits for the next tick once the caller runs `review-converse.yml`, or longer when more wait than one tick takes (eight per pull request, `max-pull-requests` pull requests) or the run fails; without it, until the next push or command run.
- When a reply-only run's summary write fails after it answered, it still sets the status and syncs the label from what it computed (a waiting thread sets `needs owner` and `failure`; with none the status stays) and reports the failure, since `find` will not list the pull request again once the bot's answer is the latest comment. The summary's verdict line and waiting list stay stale until the next run that writes the summary; the status sweep reconciles the status from the bot's `needs-owner` answers meanwhile.
- A failed label write is tried again on every run while a thread waits; a failed removal is not retried once the list is empty.
- Rejected for commands: the slash form; a default handle without the app; a handle read from the comment; `author_association` as a filter (a private organization member can show as a contributor).
- Rejected: the identity inside the marker (GitHub attests the author, the marker is text); numeric bot ids in the config (slugs are what GraphQL and REST return and what a person can read); a second, read-only family of workflow files for app mode; editing the old summary in place (it breaks the rule that the bot edits only what its current identity wrote, and the summary would keep the old name).
