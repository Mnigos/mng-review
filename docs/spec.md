# MNG Review: specification

Pull request review by one built-in reviewer and the agents a repository declares. The engine is a Bun + TypeScript package (`@mnigos/mng-review`, binary `mng-review`) used three ways: a CLI, a reusable GitHub workflow and a library. It talks to any OpenAI-compatible chat completions endpoint.

## Packages

A Bun workspace on Effect 4. Dependencies point one way: `cli` and `action` use `engine`, which uses `domain`.

| Workspace | Package | Holds |
|---|---|---|
| `packages/domain` | `@mng-review/domain` | Schemas and pure logic: config and agent file schemas, selection rules, findings, fingerprints, severities. No services, no runtime. |
| `packages/engine` | `@mng-review/engine` | Effect services: config loading, git, the model endpoint, routing, review and validation. |
| `apps/cli` | `@mng-review/cli` | The `mng-review` binary on `effect/cli`; the only place that runs effects. |
| `apps/action` | `@mng-review/action` | The GitHub workflow entry; runs effects in its own `main.ts`. |
| `packages/github` | later | Threads, summary, checks and commands on GitHub (stage 4). |

A later stage publishes a bundled build of `apps/cli` as `@mnigos/mng-review`. ADR 0001 records the layout.

## Roles

The conductor is code. Models do five jobs:

| Role | Defined by | Job |
|---|---|---|
| Router | engine | adds agents the path rules missed and names what makes the change risky |
| Main reviewer | engine, steered by `.mng/CONTEXT.md` | finds bugs across files; runs on every change that is not `trivial` |
| Declared agents | `.mng/agents/*.md` | `kind: bug` specialists and `kind: nit` convention checks |
| Validator | engine | tries to refute each bug finding before it is posted |
| Verdict | engine | `ready`, `needs fixes` or `needs owner` |

The router model only routes. The main reviewer and the validator run on the reviewer models, by default `gpt-6.1-sol` and `claude-opus-5-5` at high effort. Declared agents run on `models.agents`, by default `gpt-6.1-sol` at high effort. All models go through the same OpenAI-compatible endpoint.

## `.mng/` layout

```
.mng/
  review.yml     # settings
  CONTEXT.md     # for the main reviewer: intentional patterns, where bugs hide
  MEMORY.md      # accepted "intentional" decisions, one line each
  agents/        # declared agents, one Markdown file each
```

## Agent file

YAML front matter plus instructions. `@/path#Heading` imports one section of a file, read from the base commit. Front matter overrides `review.yml` for that agent.

```markdown
---
title: Auth and ownership
kind: bug                 # bug: validated, own thread | nit: batched, never blocking
when:
  paths: ['packages/auth/**', 'src/**/*.guard.ts']
  exclude: ['**/*.spec.ts']
  labels: []              # optional: any of
  authors: []             # optional
  targets: []             # optional: base branches
  triage: 'changes who can read or write which data, sessions, tokens or roles'
model: gpt-6.1-sol
effort: high
input: incremental        # incremental | full_diff | metadata
needs: []                 # check names that must pass first
max_findings: 8
---
Trace every changed handler to the check that proves the caller owns the row.
@/docs/auth.md#Rules
```

`when.triage` is the sentence the router reads to decide whether to add this agent when no path matched.

Selection rules: every non-empty `when` list must match. `labels` needs any one of the pull request's labels, `authors` the author, `targets` the base branch, and `paths` at least one changed file that no `exclude` pattern matches; a renamed file matches at its old or new path. An agent without `paths` covers every changed file. Only an agent that failed on `paths` alone, and has a `triage` line, is offered to the router. Patterns are globs; a pattern without a `/` matches the file name in any directory.

Import lines stand alone on their line. `@/path` imports the whole file and `@/path#Heading` the section from that heading to the next heading of the same or a higher level. A missing file or heading fails the run.

## `review.yml`

Every key has a default in the engine preset. Unknown keys fail the run and name the key.

```yaml
extends: mng:default

features:                        # always | manual | off
  reviewer: always
  agents: always
  verdict: always

depth: auto                      # auto | quick | balanced | deep; auto = router's risk level
risk_paths: []                   # changes here are deep, unless the change is mechanical

comments:
  min_severity: medium           # bugs below this go to the summary only
  max_nits: 5                    # inline nits per run; the rest in the summary
  summary: true

limits:
  max_runs_per_pr: 6
  max_file_kb: 300
  tokens_per_run: 2000000         # hard cap of one run; finders plan at most 70% of it
  tokens_by_depth: {quick: 100000, balanced: 300000, deep: 800000}   # what a run plans to spend
  tokens_per_pr: 5000000
  concurrency: 4

skip:
  drafts: true
  forks: true
  authors: ['dependabot[bot]', 'renovate[bot]']
  labels: [skip-review]
  targets: []
  paths: []
labels:
  always_review: [review]
  depth: {quick: mng-review-quick, deep: mng-review-deep}

commands:
  allow: []                      # logins besides admins that may run commands, with write access
  max_runs: 3                    # command runs per pull request, counted before the endpoint is used

disputes:
  accept_intentional_up_to: medium
  max_rounds: 1
verdict:
  blocking_severity: medium
  mode: approve                  # approve | preview; preview never approves
  never_approve: []

models:
  router:    {model: gpt-6-luna, effort: low}
  reviewer:                      # first finds, second validates; all find when risky
    - {model: gpt-6.1-sol, effort: high}
    - {model: claude-opus-5-5, effort: high}
  agents:    {model: gpt-6.1-sol, effort: high}   # a declared agent may override model and effort
  validator: cross               # or an explicit {model, effort}

identity:
  previous: [github-actions]     # bots whose earlier comments still count as the bot's

risk:                            # the risk rating; see Risk rating
  enabled: false
  labels: {low: Low Risk, medium: Medium Risk, high: High Risk}   # one at a time, display only
  floors: []                     # [{name, paths, exclude: [], level: medium | high}]
  assets: ['*.png', '*.jpg', …, '*.pdf']   # binaries the rater may leave unread
  reviews_per_head: 3            # `review` commands that rate one head
  model: validator               # the rater: `validator` (models.validator, else the reviewers) or {model, effort}
```

## Pipeline

1. **Gate.** Apply `skip` and `features`. Wait for the checks an agent lists in `needs`. The same head, merge-base and config hash as the last run reuses the verdict.
2. **Route.** Paths, labels, authors and target branch select agents. The router model then reads the path list, a truncated diff and the `when.triage` line of each agent that failed on `paths` alone. It returns agents to add, one reason each, and risk signals: each names a category, a changed file and the lines in it. The categories are `access` (the check that decides who is signed in or may read or change something), `money` (charges, refunds, prices, entitlements), `stored_data` (schemas, migrations, updates or deletes of existing records) and `secrets` (credentials, keys, and what personal data goes to logs or other services); code that only calls an existing check, reads data or renders it is not a signal. The engine drops a signal whose file is not a reviewable changed file and derives the risk level by rule: `risky` with at least one signal, else `trivial` when the router marked the change as having no runtime effect, else `normal`. The model reports what the change does; the threshold is code, so the same change gets the same depth. The path list it reads is sorted. It can add agents and never removes one. A change under `risk_paths` is `risky`, unless the change is mechanical: at least 50 reviewable files, at least 60% of them small edits (at most 10 changed lines), added and removed lines within 25% of each other, and no file under `risk_paths` rewritten (50 or more added plus removed lines; an edit to a risky file below that passes this condition, so when the others pass too the router's rating is capped at `normal`). A lint or format migration fits, the few dozen lines it often changes in configuration under `risk_paths` included; it is at most `normal` whatever the router says. When files under `risk_paths` changed, `plan` and the review output print the measured values against each limit and the conditions that failed, and the JSON carries them as `risk.shape`. If the router fails, the run continues with path selection and `normal`.
3. **Depth.** `trivial`: metadata agents only. `normal`: the first reviewer model runs the main reviewer, and selected agents run once. `risky`: every reviewer model runs the main reviewer on its own, each as one sub-agent per changed unit (function, handler, migration; up to 8 in parallel, fewer when the budget below pays for fewer and more when the diff is large, one per 60,000 diff characters; when there are more files than units, the files are taken in path order and each unit closes once it holds its even share of the changed lines, so a unit keeps neighbouring files together). When `risk_paths` made the run deep, reviewer models after the first review only the units under those paths; when the router's signals made it deep, only the units of the files the signals name. Such a narrowed reviewer model plans tokens for the lines it reviews: its share times the changed lines of those files over all changed lines, at least a quarter of its share.

   **Token budget.** A run plans to spend `limits.tokens_by_depth` for its depth, never more than `limits.tokens_per_run`. 70% goes to the finders, split by weight: the main reviewer 4, a bug agent 2, a nit agent 1, its share split evenly over its units; the main reviewer runs get at least 40% of it together, the agents splitting the rest by weight, so many selected agents do not leave the one cross-file finder a few calls; the rest goes to validation, shared by the bug findings (30k to 60k each, so many findings can take a run past its plan). A finder that answers under its share gives the rest to the run's pool, and a main reviewer conversation that would otherwise have to answer claims what it lacks from the pool first, so tokens an agent did not need go to the one cross-file finder instead of being left unspent. Each conversation re-sends its first message on every call, so the first message's diff takes at most 15% of the conversation's share, and the conversation reads the rest with tools. A conversation answers with what it has once it could not afford two more calls (each costs at least the input of the one before; before the first call the first message's length is the estimate), so a first message that takes more than half the share is answered in one call; a turn's tool outputs are refused only when they would not fit before the answer call; and every finder answers once the finders' 70% is spent. Each main reviewer conversation is then sized by what it must read (ADR 0013): its first message, every part of the diff of each file the first message cuts and 10,000 tokens around them, read over at least three turns of at most six reads each and answered, under the two rules above with 1,000 output tokens a call. Where its share is smaller, the run grants the difference and plans that much more, while the finders together stay within 70% of `limits.tokens_per_run`; past that every grant is cut by the same factor, the report records the cap (`capped`), and the run does not approve. The sizing estimates 3 characters a token, which some tokenizers exceed, so after a granted conversation's first call its grant grows by the call's real input tokens over that estimate (its token rate, never below 1), taken from what is left under the same cap; when that runs out the conversation gets what is left and the report records the cap. Each agent report lists its conversations' rates (`tokenRates`). So a run costs about its planned tokens whatever the number of agents; more agents get smaller shares.
4. **Find.** Each reviewer is a tool loop over chat completions. Tools are read-only and confined to the repository: `read_file(ref, path, range)`, `grep(ref, pattern, glob)`, `list_dir(ref, path)`, `diff(path?)`, `blame(path, range)`, `pr_metadata()`. Head content is read with `git show`; nothing from the change is built or executed. Change text and tool output are passed as fenced data. A finder's first message lists every changed file with its line counts, skipped files and their reason included, and carries the diff budgeted across files rather than cut in path order: from the smallest file diff up, a file that fits an even share of what is left is shown whole and a larger one is cut to that share; once the share is too small to be useful, files are shown whole while they fit, and what is left goes to the rest as excerpts of at least 600 characters, smallest first. The file list marks every cut or left-out file and names, for each of them, up to four functions or blocks its hunks change (the context git prints after `@@`), and the message tells the agent to read those with `diff(path)` before it answers; a long diff comes back in parts, each ending with the offset of the next. Output: findings as JSON `{path, line, severity, title, trigger, impact, evidence[], suggestion?}`. The report instructions carry the writing rules a comment needs (plain words, whole sentences in the active voice, one idea per sentence, no hedging, filler or em dashes), and the text has limits: a title of one line and at most 100 characters, an impact of at most 450, a fix of one line and at most 300, a trigger as one step per line of at most 200 characters. The prompts ask for these limits; text that runs over is cut at a word boundary and ended with `…`, so a limit never drops a finding or costs a turn. Findings with the same root cause merge and record every model and agent that reported them: same kind and path, and the same fingerprint, or lines at most 6 apart with similar titles, or lines at most 6 apart from different finders whose title, trigger and impact share at least half of the shorter description's words and whose titles and impacts share at least 40%, so a common trigger alone never merges two failures. A report that matches several merged findings joins them all unless one finder would then hold two distinct reports. The main reviewer's method is checked, not only asked for: before its answer counts it must have received every changed file in its scope whole, by the test below. Its first message, its continuation turn and the descriptions of `diff` and `read_file` steer each cut file to every part of `diff(path)`, since `read_file` never shows what a change deletes. When it answers with files unread and its tool calls, wall time and tokens allow another turn, it gets one continuation turn naming them with why each is unread (not read, only part of its diff came back, or read with `read_file` though the change deletes lines; at most 20, the rest counted); its findings so far are kept, the continuation adds only findings that do not repeat them, and a continuation that fails keeps the first answer. The report counts the conversations that got one, and the changed files each main reviewer answered without receiving whole (`unread`, and `unreadFiles` with each path and its reason, which the result file carries and the review body lists), which keeps the run from approving: a file counts as read only when its first message showed its whole diff, every part of its diff came back from `diff`, or, for a file that deletes no line, `read_file` at the head showed every added line (a read of the head never shows what a deletion removed); a partial `read_file`, `blame`, one part of a long diff or a finding on the file never does, and when a continuation fails the kept answer counts only the outputs the model had received when it gave that answer. A model that answers 429, 503 or "unknown model" is dropped for the rest of the run; the run goes on with the remaining models and reports the drop. With no reviewer model left the run fails. Finders answer within the token budget described under Depth; no model call starts once `limits.tokens_per_run` is spent. A finder or unit stopped before it answered, and a validation that could not run, are named in the report, which is marked incomplete; every finding already produced is kept (an agent's `max_findings` still applies), and a finding whose validation did not run is kept as unvalidated.
5. **Validate.** One fresh agent per bug finding, instructed to refute it. With `validator: cross` it runs on a reviewer model that did not report the finding; a finding every reviewer model reported, or a run with a single reviewer model, is validated once by a reviewer model in a fresh context. An explicit `validator: {model, effort}` validates everything. It receives the finding, 150 lines either side of it at head, the diff, `CONTEXT.md`, `MEMORY.md` and earlier threads on that file. It answers confirm, reject or unverified, a severity by the rubric (see Severity) and `path:line` evidence. It rejects only with lines of this repository that show the finding is wrong: a trigger that cannot happen here or none named, a wrong premise about this repository's code, a dependency behaviour that the repository's type declarations, manifests, lockfile, vendored code or tests contradict, repeats of open threads, anything `MEMORY.md` or `CONTEXT.md` covers, and style rather than behaviour. Its memory of a dependency is not evidence. `unverified` is for a finding whose premises about the repository hold but which rests on a dependency's behaviour the repository neither shows nor rules out; the answer names that behaviour as `premise` (one sentence of at most 300 characters; `reason` at most 800; either is cut at a word boundary when it runs over, never rejected). A confirmation may carry `edit`, the fix as one edit of the finding's line: that line's text at head and its replacement. The engine keeps it only when the text matches the line at the head, the replacement changes it, holds no control or format characters and stays within 20 lines and 2,000 characters. The engine enforces two rules on every answer: a rejection whose evidence names no file at the head or the merge base and no rules file is kept as unverified at the reported severity, and a severity below the reported one without `lowered_because` is replaced by the reported one; both leave a note in the validation. An unverified finding is kept at the validator's severity, reported after the confirmed ones, and never blocks (ADR 0005); in publish mode one at or above its severity floor gets a thread marked unverified, one below it appears only in the summary. A finding the validator cannot answer for after two attempts is kept. Bugs the text match left apart but that sit on the same path at most 6 lines apart, from different finders, are validated as a group: the most severe is validated with the others listed as nearby findings, and its validator names in `same_root_cause` those that describe the same defect. They merge into it with every agent and model recorded and are not validated again; the rest of the group goes on the same way. A rejected or unvalidated finding merges nothing, and one finder's own reports are never offered as duplicates.
6. **Publish.** Only in publish mode (see CI). Bugs placed inline get one inline thread each. Above the fold: a severity marker (🔴 critical, 🟠 high, 🟡 medium, 🔵 low, ❔ unverified, none for a nit; the review body and the check run use the same ones), the title, the impact and the fix, with a GitHub suggestion when the validator's `edit` passed the engine's check, the comment sits on that line, the head is the one it was checked at, and publishing's own read of that line at the head equals the edit's original text. The outcome file comes from a job that runs model code, so on a mismatch or a failed read the comment is posted without the suggestion. Folded: why an unverified finding does not block, the trigger as numbered steps, the evidence as `path:line` links to the head, and a prompt for a coding agent in a plain text block. A footer names the agents that found it and the validator model that confirmed it, as people know the model. A hidden marker (`id`, `kind`, `agent`, `severity`, `fingerprint`, `title`, engine commit) ends the comment; later runs match threads by it, never by the text, so threads posted with an older layout keep matching. Unverified bugs at or above their severity floor get a thread marked unverified that never blocks. Nits placed inline (at most `comments.max_nits`) go into the same review; the rest are listed in the summary. A finding covered by an open thread of the bot (same fingerprint, the same line of an open thread whatever the title, or a nearby line with a similar title; an unverified thread never covers a confirmed bug), or only by resolved ones whose code within 6 lines no commit has touched since, is not posted again. A line outside the diff gets a comment on its file; a file outside the diff goes to the summary. A run whose list reads left a null node out (ADR 0012) puts every new finding in the summary instead of on a line or file, since the node may be the bot's thread for it; the next run with complete reads posts the ones still new. A finding only `metadata` agents reported is about the pull request, not a line, so it goes to the summary under "About the pull request" whatever place it names; a bug there still blocks. The summary is the body of the run's review (ADR 0010): one review per run, with the new line threads as its comments, edited in place instead when the run posts no thread and the bot's newest review is its current identity's, visible and in the state the run keeps or posts (an approval or a change request only by a run on the current head, the pull request's head as the write reads it right before the review, again before the cleanup and once more before the dismissals), and each new review hides the bot's earlier ones as outdated, except an approval or change request on the current head when the run reviewed another, and every approval or change request when the current head could not be read. A push between the run's head check and the write's head read makes the run partial: its marker keeps the previous head and flags. The review's state carries the verdict (ADR 0011) and changes only with evidence for the new state: `REQUEST_CHANGES` when a run on the current head (a reply-only run also on the head of the last full review) leaves a confirmed bug thread (or a bug without a thread) open or a thread waiting for the owner; `APPROVE` only for a push or a command that named no agent that finished `ready` on the current head (read again before the event is picked) and covered the whole change: the main reviewer ran (a quick review never approves) and read every changed file in its scope, every planned run reported `ok` with no failed or timed-out unit, the token budget stopped nothing, no changed file was skipped as binary or too large, no finding was kept (unverified, below the floor or nit) and no unverified or nit thread of the bot is open in publishing's second thread read (a failed read approves and clears nothing), when `verdict.mode` is `approve`, the bot is not the job token's `github-actions` and the write's head read shows the pull request open and not a draft (a draft, closed or merged one keeps the state, and so does a read that fails, which the body names as such rather than as a draft); `COMMENT` for such a run that did not cover the change only through findings that never block, skipped files or files left unread, and for a reply-only run that finds the head of the last full review `ready` after a full review with no failed run, when its second thread read succeeded. Every other run keeps the state and posts `COMMENT` when it must post (an offline run, a run whose head is not the current one or could not be read, one agent or a run that did not finish and found nothing blocking, a run with a failed, missing or erroring run or unit, a reply-only run that is not `ready` on that head, a run whose list reads left a null node out): it edits the newest review, never an approval or change request on another commit or, for a run whose head is not the current one, on the current head. A standing owned change request (the identity's newest approval or change request, dismissed ones aside) is kept as `REQUEST_CHANGES` only by a reply-only run on the current head that finds something blocking off the last full review's head. On a pull request the bot opened every state is `COMMENT`, offline runs included. The body opens with a line naming the state it lands in (`**Approved.**`, `**Changes requested.**`, `**Comment.**`) and, unless it is a fresh approval, one sentence of fixed text and counts on why the bot did not approve; for a run whose list reads left a null node out, first, "a list GitHub returned was incomplete (reviews), so this run did not approve, lift a change request or clear a wait.", naming each such list, then any other reason. A run whose list reads left a null node out never raises approval: it does not approve, write a `success` status, lift a change request or clear a wait. It may always lower approval: it still dismisses the bot's own stale and replaced approvals and the review a push outlived, and turns a `success` status into `pending` when the head's status can be read, also when its summary write fails (a reply-only run writes the status its standing gives, a full run `error`). Such a run never edits an approval of the current identity but posts a `COMMENT` review over it (GitHub still counts that approval toward required approvals); the write's own reads count too (not the read that confirms a create GitHub answered with an error, which comes after the decision and keeps its own count), so a write whose read left a node out attaches no inline comment, keeps every wait and never removes the `needs-owner` label, and file comments wait for the last thread read. Its `MNG Review` status is `pending`, naming the lists, where it would be `success` over no status or a `success`, keeps a `pending`, `failure` or `error`, and writes a `failure` or `error` as usual, also when the head's status cannot be read; a clean agent's check run is `neutral`. Only a write that clears (an approval, a full finished `ready` run with no failed run, a clearing reply-only run) dismisses the owned change requests; when the head read after the write shows another commit than the review the write left, that review is dismissed when it approves, or when it requests changes and this write posted it, while a change request the write only edited keeps its evidence and stays until a clearing write; every write dismisses the owned approvals that are not the current identity's on the current head, except that a run whose head is not the current one never dismisses an approval on the current head, and a write that could not read the current head dismisses none; the sweep dismisses the current identity's change requests it read before the threads when no open bug thread, no bug without a thread on the marker's head and nothing waiting remain, finished or not (with the marker on another head, only change requests on a known commit other than the pull request's head), only after its status write passed the freshness check, or with no write due while the status keeps its writer and state, only while a read of the head right before the dismissal still shows the head it judged, and never one that its second review read, made before it decides the status, shows edited or in another state, nor on a pull request whose list reads left a null node out (counted per pull request, that second review read included), where it turns a `success` into `pending` instead; a failed read on the way counts the pull request as failed in the sweep's result, beside a status it updated. Dismissals GitHub refuses are reported in the job log and the result file and tried again later. It shows the verdict line first (`ready`, `needs fixes`, `needs owner`, or `incomplete` when nothing blocks but the run did not finish), the risk level and what decided it, run N of `limits.max_runs_per_pr`, then new threads, findings below the floor and nits in the summary, rejected findings (collapsed), the agents skipped and what did not finish, and, folded, the agents that ran with their results and why and the tokens per model. Its marker, in the newest summary review of an owned identity (hidden or dismissed ones included), or before the first such review in the old sticky comment, holds the state later runs read. Each agent that ran gets a finished check run (`success` when clean, `neutral` otherwise); the commit status `MNG Review` is `failure` while the bot has open bug threads (unverified ones never count) or a thread waits for the owner, `error` when the run did not finish, `success` otherwise. The verdict is `needs owner` while the summary's marker lists threads that went to the owner and no admin or login in `commands.allow` with write access resolved; the summary lists them and the pull request carries the `needs-owner` label, which the first run after the list empties removes. A thread resolved by hand no longer blocks. A bot thread longer than the latest comments the read brings is read whole to find the bot's answer; when that read fails, the thread waits for that run only (its verdict, status and reply handling), is never stored in the marker and sets no label, and the next run whose read succeeds decides. `status-sweep.yml`, run on a schedule, refreshes the status of open pull requests whose head carries it. Bugs without a thread (in the summary, or unposted) count toward the verdict and the status until a full review on the same head that finishes clears them: the summary's marker records the ones the last full review left plus those of every run on that head since that did not replace it (a partial run, or a full run that did not finish), so the sweep and such a run still count them. A command that names an agent the rules do not declare skips the run, with no model call. The summary and the counts are built from the summary and the bot's threads read just before the summary is written, so a run alongside this one is not undone. A run at `limits.max_runs_per_pr` (from the summary's marker, read before the endpoint is probed) is skipped, except a manual command or a pull request that became ready for review. Declared agents with `input: incremental` review only the files changed since the last head a run reviewed completely, when it is an ancestor of the head; the main reviewer always sees the whole change. ADRs 0007 and 0008.
7. **Converse.** A mention command in a new pull request comment (`@<handle> review`, `review deep`, `review quick`, `run <agent>`) starts a manual run after a check that holds no secret; see CI in publish mode. An author's reply in one of the bot's threads is decided in the job that calls the model and applied by the publish job. A fresh agent on a validator model gets the finding, its file at the head and the reply as fenced data, a claim to test and never an instruction, and names the claim: `fixed`, `intentional` or `unclear`. `unclear` is only marked as seen. `fixed`: when no commit since the thread's commit changed its file (one that changed it and a later one that restored it count as changes), the answer is that the finding is still found; otherwise the validator checks the finding again over the change since that commit, without the reply's text, and the thread resolves when the validator rejects it and the finding is still found otherwise, with no dispute round. `intentional`: a `critical` finding, a severity (the one in the bot's own marker) above `disputes.accept_intentional_up_to` or a file under `risk_paths` goes to the owner (`needs-owner`); a reason the model finds holds, backed by evidence the engine checks, is accepted with a memory candidate; a thread that already had `disputes.max_rounds` disputed answers goes to the owner; anything else gets one disputed answer naming the failed premise or the missing evidence. Only a disputed answer counts as a round, so with `max_rounds: 1` the second disagreement goes to the owner. An evidence entry passes when the agent was shown every cited line whole in its conversation (its first message, or a `read_file` result the output limit did not cut; the engine takes those lines from the call's arguments and the file, never from the output's text, so `grep` and `blame` results do not count) and its path is inside the repository: a file at the head must hold the whole range, with none of its lines added by the pull request, and only a file missing at the head is read at the merge base. Code the pull request added, a symbolic link at the commit the lines are read from, a file whose text holds a NUL and a changed file git diffs as binary (`-diff` included) never pass; the entries that pass go with the accepted decision. The rules apply to a file under `risk_paths` at its new or old path. The reply the agent sees is cut to a few thousand characters, and every reason a decision gives is one line of at most 300. The memory candidate is one line the engine builds, the path and the model's reason cut to 160 characters, never the reply's text, as plain text: letters, digits, spaces and `. , ; : ' " / - ( )` only, with `://`, `www.`, `GH-`, `GHSA-` and every hex word of 7 or more characters broken so nothing renders as a link, reference or emphasis, and is trusted only once a person merges it into `.mng/MEMORY.md`. A failure of the model, git, the token budget or the re-check leaves the reply seen, unanswered, so the next run tries it again; a thread commit that is no longer an ancestor of the head is not re-checked, and the finding is still found. Replies are answered in the push and command runs that are not skipped (a push at `limits.max_runs_per_pr` leaves them for the schedule), and by `review-converse.yml` on the caller's schedule from the default branch, so the next tick picks up a reply that came without a push, unless more wait than one tick takes or the run fails, which leaves them for a later tick: its `find` step lists the open, same-repository pull requests that are not drafts with a reply waiting, at most `max-pull-requests` per tick, oldest reply first and rotated by the run number when more wait; for each, the review leg probes the endpoint and only decides on the replies, and the publish leg answers them with the checks a push run's publish job makes and updates the waiting list, the verdict and the status, leaving the run count, head, finished flag and unthreaded bugs as they were and posting no thread or check run. Such a run is not gated by `skip` rules or run limits and counts toward neither. In those push and command runs the prepare step takes the latest comment of each open bug or unverified thread of the bot when a `User` with write access wrote it and it ends with no marker, at most eight per run, rotated, and never in a thread that waits for the owner; the review step decides them after the re-check, and the publish job answers only when its own read still shows the same comment, unedited, as the latest and its author still has write access, and reads the thread once more right before each answer (the reply mutation has no precondition, so a small window remains); it drops an `accepted` decision on a finding past the owner's limit, which it checks from the bot's marker, the base commit's rules and the files git shows changed between the bound base and head, never from the outcome file. It also checks closing decisions with its own git reads: `resolved` stands only when the thread's commit is an ancestor of the head and a later commit touched the finding's file, and `accepted` only with at least one evidence entry that passes the evidence rules again at the bound commits (whether the agent was shown the lines rests on the review job); the answer shows the entries that pass. A finding whose thread the run closes is not posted again; later runs count changes to its code from the head of the closing answer. Each answer ends with a reply marker naming the comment it answers. `resolved` and `accepted` close the thread for the bot's counts; `needs-owner` is one final answer, which publishing accepts only past the `intentional` limit or `disputes.max_rounds` as its own read counts them; its thread id goes into the summary's marker, a thread holding that answer waits, open or resolved, even when the marker lost the id or a writer hid the summary (hidden summaries of owned identities are still read), until an admin or an allowed login resolves it, and the pull request gets the `needs-owner` label. On every push the bot re-checks its open threads whose file changed since their commit, when they have no reply and the run did not find the same problem: the validator gets the finding and the change from the thread's commit, in the review job; a rejection becomes a proposal in the outcome file, and the publish job, after it rereads the thread, writes a one-line reply naming the head and the reason, which closes the thread for the bot's counts (resolving it on GitHub needs `contents: write`, which the job does not have). ADR 0008.
8. **Learn.** Accepted decisions are proposed for `.mng/MEMORY.md` in a periodic pull request. A periodic report lists findings, fixes, dismissals and tokens per agent.

## Severity

Finders rate a bug by what goes wrong when its trigger happens, and the validator re-rates it with the same rubric (`SEVERITY_CRITERIA` in `packages/domain`). The level is the highest one whose criterion the impact meets:

| Severity | Criterion |
|---|---|
| `critical` | data is lost or corrupted, or a security boundary fails: private data, credentials, money or access reach someone who should not have them |
| `high` | the program crashes, a request or a main flow fails, or users get wrong data, shown to them or stored |
| `medium` | behaviour a user can see is broken, but the user can recover: retry, reload, undo or take another path |
| `low` | cosmetic, or nothing a user can reach: only logs, metrics or developer tooling change |

How often the trigger happens does not change the level, and neither does how many users it reaches: a defect on one platform, browser, locale, user setting or assistive technology rates the same as one that hits everyone. A trigger that cannot happen is a reason to reject, not to lower. The validator starts from the reported severity and may raise it; it lowers it only by naming, in `lowered_because`, the reported level and the part of its criterion the impact does not meet. Nits are always `low`.

## Risk rating

With `risk.enabled` and the app in an environment (`app-slug` and `app-environment`), publish rates how much a pull request into the default branch needs its owner. ADR 0012.

- **The status.** The app writes `MNG Review risk` on the head: `success` at Low and Medium, `failure` at High, `error` when not rated. The description has one form, `v1 pr=<n> <low|medium|high|none> floor=<yes|-> base=<merge base> rules=<12 hex> nonce=<16 hex>`; `rules` is a sha256 prefix over the built-in floor version, the resolved rubric (`.mng/risk.md` and its imports) and the merged `risk` keys. Readers take only the app's statuses for their own pull request number and reject any other text. Only `success` at `low` or `medium` grants. The label (`risk.labels`) is display only, and the bot never sets or removes `Blocked`.
- **Floors.** Publish reads `git diff --no-renames --raw --numstat -z` from the merge base itself; a rename counts at its old and its new path. The built-in floor sets High and `floor=yes` for every added, changed or deleted file under `.github/**` or `.mng/**`, `CODEOWNERS` at the root or in `docs/`, `.gitattributes` at any path and every file the rules resolve to, and for any submodule, symlink or mode change; paths compare without case and no config removes it. `risk.floors[]` adds named critical areas (`paths`, `exclude`, `level`, Medium by default); names are lowercase letters, digits and hyphens, each used once. A binary outside `risk.assets` leaves the pull request unrated, and a count that does not parse, or output that does not parse whole, means High.
- **The level** is the highest of the rater's level (or the stored level of a rated head with the same tree, base and rules digest), every floor, Medium for a router `risky`, High for an open or carried confirmed High or Critical bug, the marker's highest, the highest level a person's edit anywhere in the marker comment's edit history names (any valid marker form in its text, High when GitHub does not give the text or lists the edit as a null node) and the held level, the highest level on any app status for the pull request, `error` included, from the current app or one in `identity.previous` (never the job token). Nothing lowers it.
- **The rater.** After Validate, a full run with `risk.enabled` (push, `review`, a dispatched `review`; not `run <agent>`, reply-only or converse) rates the change on `risk.model`. One fresh agent reads the rubric, every changed file with its status and counts (`skip.paths` included), the diff of the complete change cut to the first-message budget, the floors, the kept findings and the earlier rating; it reads code only with `read_file`, `grep`, `list_dir` and `diff`, never the title, description, comments, commit messages or `blame`. It answers `report_risk` with a level, one to three reasons, `refs`, `up` and `down`; long reasons are cut, never refused. The rating counts only when the engine's read check passes over every changed file but `risk.assets` binaries: each one's whole diff in the first message or through `diff`, or `read_file` at the head over every added line, and a file with a deleted line only through its whole diff. A review where any finder failed, only partly ran or was stopped by the token budget, a rater answer the token budget forced, a binary outside `risk.assets`, a coverage gap, a malformed answer or a failed rater leaves the change unrated. `mng-review --json` prints it as `rating` on a run that rates.
- **Write order.** Every writer runs in the job-level group `mng-review-risk-<number>`. A full run writes `error` at the higher of the held level and its own level and reads it back, posts the review, checks its nonce, updates the marker from its current trusted text, checks its nonce again, sets the label, re-reads the head, the base branch, the merge base, the nonce, the marker, the confirmed bug threads (below High) and the held level over every head, and writes the grant last. It then reads the statuses again: a grant it cannot confirm, or one a higher level landed just before, gets step 1's `error` again, and when that write is refused the job fails. A thread run writes step 1 after its posts, so its held read follows them. A failure after step 1 leaves `error` at that level, and a refused `MNG Review` status is such a failure; a failed read or write before it fails the job, and so does a grant that could not be read back or revoked. A run that finds another run's nonce newest changes neither the status nor the label. GitHub has no conditional write, so until the workflows put every writer in the group, a marker update can overwrite another run's entry, and a cleanup can revoke a newer run's status. Every full run reads the marker comment's whole edit history (every page, at most 500 edits, more fails closed) before step 1, so a person's edit a marker write overwrote counts in the next full run; a history it cannot read leaves it unrated. A person's edit the update overwrites leaves the run unrated, read from that history before and after the write and matched by edit id, which still works at GitHub's 100-edit retention; a history that does not list the run's own update yet is read again three times, two seconds apart. A level above the run's that the history read before the write names, or a null node that history did not list, leaves it unrated too. The rewrite of an edited marker writes no second status. A person's risk label above the status level does not raise the status, but the merge tool refuses the pull request (ADR 0012). The label step reads the timeline again after its second label read, just before its writes. A held read fails, and the pull request stays unrated, on a 404 for a head's statuses, a timeline commit without its commit or a timeline item listed as a null node. While the rating is on (every step whose rules set `risk.enabled`, publish included, also when its gate refuses the run), review threads, a thread's comments, conversation comments and reviews fail on a null node too, as a failed read; deny, risk cleanup, the risk sweep and any entry point that provides nothing read complete lists as well. Only rules with the rating off leave the node out, so a null entry never fails their publish; every such read counts what it left out and which list it was, and the run is then incomplete: it posts its new findings in the summary, never raises approval (no approval, `success`, lifted change request or cleared wait) but may still lower it, and its review headline says so (Publish). A whole-thread read that left a comment out counts as a failed read. With the rating on, one null node fails the run even when its gate is refused: it fails closed (a refused publish reports a failure without a rating and its job still passes; what it posted before the failing read stays), and until GitHub lists the node again the only ways out are turning `risk.enabled` off or deleting that entry; with the rating off the run publishes but stays incomplete, so it approves nothing, lifts no change request and clears no wait until the entry is gone. The timeline and the confirmed thread read behind a grant or a thread raise always fail on one. An edit history keeps a null node as an edit whose editor and text are unknown.
- **Cleanup.** `MNG_REVIEW_MODE=risk-cleanup` runs after a failed or cancelled publish step. It writes step 1's `error` again, only while its nonce is the newest status (or when the statuses cannot be read), and removes the bot's risk label; without a description it only removes the label. Settings: `MNG_REVIEW_TARGET_PR`, `MNG_REVIEW_TARGET_BASE` and `MNG_REVIEW_TARGET_HEAD`, `MNG_REVIEW_RISK_DESCRIPTION` from the publish step's `risk-description` output, and the app token (`MNG_REVIEW_APP_SLUG`, `MNG_REVIEW_APP_TOKEN`, `MNG_REVIEW_MINTED_APP_SLUG`). The publish step rates with `MNG_REVIEW_APP_ENVIRONMENT`, `MNG_REVIEW_DEFAULT_BRANCH`, the app token and `GITHUB_OUTPUT`, where it puts `risk-description`.
- **Runs.** A full run (push, `review`, a dispatched `review`) publishes the combined level, or `error` when it failed, a coverage gap or an opaque binary left it unrated, a thread or marker read failed, the marker was edited by someone else, the head moved or the nonce was lost. A `run <agent>`, reply-only, converse or sweep run only raises to High for a confirmed High or Critical bug. A `review` over `risk.reviews_per_head` on one head, a refused command and a bridge run write no status. A run with no app environment, a gate skip, an invalid `.mng/`, a fork or another base writes nothing, and the label job removes risk labels on every push.
- **Comments.** Comments count only from a person, not posted through an app and not an owned bot or `github-actions[bot]`, whose collaborator role has write access. The review workflows start on `issue_comment` `created` and `edited`: an edited conversation comment starts a named run, and an edited command gets a denial instead of running (this amends ADR 0009). Every app answer's marker names the comments it handled with their id, edit time and the first 16 hex characters of the body's sha256. A role read that answers 404 means the author is no collaborator, so the comment is not acted on; any other failed role read fails the decide job.
- **Answer entries.** The merge tool parses these, so their form is a contract. An app answer ends with one marker on one line, `<!-- mng-review:<name> <json> -->`, and only that last marker counts. A converse reply's `reply` marker, a summary review's `summary` marker and a denial or cap reply's `answer` marker (`{"v":1,"answers":[…]}`) carry `answers`, a list of at most 300 entries `{run, kind, agent?, ids}`: `run` is the id of the workflow run that answered; `kind` is `converse`, `review`, `run`, `cap` or `deny`; `agent` is set on `run` entries only; `ids` lists `{id, at, digest}`, the comment's database id, its edit time as GraphQL gives it (`lastEditedAt`, or `createdAt` when unedited, as `YYYY-MM-DDTHH:MM:SSZ`) and the first 16 lowercase hex characters of the sha256 of its whole body; `created`, set on `review` and `run` entries only, is the answering run's `created_at` in the same form. A comment is answered only when an entry names its id, current edit time and current digest with a kind that fits: `converse` for a reply; `review`, `cap` or `deny` for `review`; `run` with the same agent, or `deny`, for `run <agent>`; and a `review` or `run` entry counts only when its `created` is later than the command's current edit time (the same second does not count), the merge tool's run rule, so a run queued before the command and started after it never answers it. Such a run names only the commands whose current version is older than both its review step's start and its own creation time, and a later qualifying run names the rest; a failed read of the run's creation time names none. A command and its own run created in the same second therefore hold until a later rating run or the command posted again, and the merge tool tells the owner to post it again (ADR 0012, Rollout requirements). A converse reply's `reply` marker may also carry `unsettled: true` while the app has not reopened its thread after that answer; while the current app's newest answer in a thread carries it, the thread counts as open in every bug count (a resolved thread whose latest comments do not show that answer is read whole, and a failed read counts it open) and no resolution clears its wait (with the rating off, a whole-thread read that lists that answer as a null node counts as failed, so the thread stays open and the incomplete run clears no wait), until a later publish that did not answer the thread itself reopens it and edits the flag away; that settle covers threads any owned identity started. While the rating is on, a publish that leaves an answer unsettled fails its job, so the failed-run hold applies; without the rating it logs the count and passes, and the wait and the flag stay. A converse reply names every acted-on reply in its thread its read saw unnamed, a `review` or `run <agent>` answer its command and the earlier unanswered ones of that kind, a rating review every unanswered `review` command, and a denial or cap reply the command it refuses. An edited summary keeps the earlier entries and never drops one, since a dropped entry would make its command unanswered again; a publish whose summary marker would pass 300 entries writes no summary and fails, so the head keeps its `error` status and the owner merges by hand. Model text has every `<!--` escaped, so it cannot end with a marker.
- **Trust.** Entries count only from the current app: a marker its current identity wrote and no one else edited. `identity.previous` still decides which threads and summaries are the bot's, but its answers name nothing. After an app switch, every comment the old app answered holds the pull request again until the current app answers it: the next rating names the `review` commands, while a `run <agent>` command gets no new answer and goes to the owner.
- **Denials.** The decide step (`authorize`) refuses a `review` past `risk.reviews_per_head` on the head with a cap reply, and any other refused command from an acted-on author with a denial; it puts out `answer` (`deny` or `cap`), `answer_pull`, `answer_comment` and `answer_reason`. A small job outside the group runs `MNG_REVIEW_MODE=deny` with those as `MNG_REVIEW_TARGET_PR`, `MNG_REVIEW_ANSWER_COMMENT`, `MNG_REVIEW_ANSWER_KIND` and `MNG_REVIEW_ANSWER_REASON`, plus `GITHUB_RUN_ID` and the app token; it reads `identity.previous` from the default branch checkout and posts a new comment whose `answer` marker names the command at the version it read, or nothing when the comment no longer holds it. A failed read or post fails the job (exit 1), since the command stays unanswered and nothing dispatches it again. The publish step of a rating names the run from `GITHUB_RUN_ID`, and a dispatched converse passes its reply as `MNG_REVIEW_HELD_REPLY` to the prepare and publish steps.
- **Sweep.** With the rating on, `status-sweep.yml` runs two jobs. `MNG_REVIEW_MODE=sweep` refreshes the `MNG Review` statuses as before and puts out `risk-pulls`, a JSON array of the open pull request numbers; it fails with exit 1 when it cannot list them, when the list passes its page limit (2,000 entries) or when it holds more than 256 numbers, the most one matrix can run, so no pull request is ever left out. A matrix job per number runs `MNG_REVIEW_MODE=risk-sweep` in that pull request's job-level group `mng-review-risk-<number>`: the thread raise in the write order for a confirmed High or Critical bug thread (not for a fork, another base or a draft), then at most one dispatch of the review workflow on the default branch (a `review` for a head with no app status, a converse for a thread reply no answer names, a `review` for a review body or thread a writer started with no rating since). A dispatch first passes the checks the dispatched run makes before any model call, then the repeat rule and `limits.max_runs_per_pr`. A `review` dispatch takes the rating's checks: not a fork, into the default branch, not a draft, and the gate its review job applies to the pull request it reads by number (skip labels, skipped authors and targets, with `labels.always_review`), so a pull request the rating would skip spends no dispatch. A converse dispatch keeps the converse's own checks (fork, base, draft). The repeat rule blocks a comment version once a run for it concluded with its group job `failure`, or `skipped` because its decide job refused it; a decide job that failed while its group job was skipped allows one more dispatch and a second such failure blocks; a group job that failed blocks at once. A comment the repeat rule blocks is passed over for the next comment that holds, and only when every holding comment is blocked does the pass dispatch nothing. Any failed read or write fails the job with exit 1: a failed thread raise, one that wrote `error` because it could not read the threads or whose grant may still stand, a runs list past 2,000 entries or shorter than GitHub's `total_count` (which a filtered runs search reaches at 1,000 runs), and a dispatch the pass needed while `MNG_REVIEW_DISPATCH_WORKFLOW` is empty. `sweep` fails the same way when the default branch rules do not load while the app settings would rate. Both read the rules from `HEAD` of a default branch checkout and need the app token, `MNG_REVIEW_APP_ENVIRONMENT`, `MNG_REVIEW_DEFAULT_BRANCH` and `MNG_REVIEW_DISPATCH_WORKFLOW` (the review workflow's file name; when empty the thread raise still runs and nothing is dispatched); `sweep` also needs `GITHUB_OUTPUT`, and `risk-sweep` needs `MNG_REVIEW_TARGET_PR` from the matrix, `GITHUB_REPOSITORY_ID` and `GITHUB_OUTPUT`, where its thread raise puts out `risk-description` for the cleanup. The `risk-sweep` job fetches the default branch tip and the pull request's head as git objects, since the thread raise reads their merge base, and runs `MNG_REVIEW_MODE=risk-cleanup` with that output after a failure or cancel, since a grant that may still stand fails the job.
- **Dispatches and job names.** A dispatch passes `source` (`sweep`), `number`, `kind` (`review` or `converse`), `comment` (the holding comment's id, or the pull request number for an unrated head), `version` (its 16 hex digest, or `0000000000000000`), `edited` (its edit time, or `-`) and `head`. The review workflow names its jobs so the sweep can read them from `actions/runs/<id>/jobs`: `MNG Review decide <source> <kind> <comment>@<version> <edited> <head>` for a dispatched run's first job (only a sweep dispatch passes `sweep`, and only such a name counts for the repeat rule and the run limit, so a bridge or other dispatch must pass another source or none), `MNG Review rating` for the job that runs a full rating and nothing else, and `MNG Review converse` for the job that answers replies; a `run <agent>` job must not be named `MNG Review rating`. The sweep counts only runs of that workflow whose `path` names its file (with or without the `@<ref>` the runs API may add) and whose `head_repository.id` is the repository's: comment and dispatched runs on the default branch, and push runs (`pull_request_target`) whose `pull_requests[]` names the pull request with the default branch as base, so the push run must come from the same workflow file. It lists them from the oldest comment that may hold the pull request (a reply, or the newest review body or thread a writer started; other people's never hold), or for an unrated head from the head's arrival (the last force push or commit that brought it, never later than now or the earliest force push that brought it; with no force push, the pull request's creation), never from before the pull request's creation; it lists no run when nothing may hold. The run limit counts the dispatches on the head from a separate list of the workflow's dispatched runs since the head's arrival, read only when a comment still holds; on a long-lived pull request with many dispatches that list can reach the runs search's 1,000 results, and the pass then fails closed: nothing is dispatched until the owner merges or a new head arrives. Runs in flight are listed from the pull request's creation on. The `risk-sweep` matrix job is named `MNG Review risk-sweep <number>` so the merge tool can find it (ADR 0012, Rollout requirements).

## Running it

- **CLI:** `mng-review --base <ref>` reviews the current branch and prints findings as text or JSON (`--json`). `mng-review plan --base <ref>` prints which agents would run, which are skipped and why, the router's additions and the risk level, without a review. Locally, `.mng/` is read from the working tree; `--rules-ref <ref>` reads it from a commit instead, as CI does. `mng-review init` writes a starter `.mng/`; `--from-macroscope` builds it from `.macroscope/` (see Init). `mng-review bench <file>` replays recorded changes against expected findings (see Benchmark).
- **Endpoint:** `MNG_REVIEW_LLM_URL` and `MNG_REVIEW_LLM_KEY`. Nothing else about the provider is assumed.
- **CI:** a reusable workflow, `.github/workflows/review.yml`; the caller keeps its triggers and concurrency and passes the endpoint and key as secrets. Rules are read from the base commit, so a pull request cannot change the rules it is judged by. Fork pull requests are skipped. See CI in shadow mode.
- **Commands** in a new pull request comment, from an admin or a login in `commands.allow` with write access: `@<handle> review`, `@<handle> review deep`, `@<handle> review quick`, `@<handle> run <agent>`, through `review-command.yml`. The handle is the app's slug, or the workflow's `handle` input without the app. ADR 0009.

## Init

`mng-review init` writes `review.yml` (extends `mng:default`), `CONTEXT.md` with the headings `Intentional patterns, not bugs` and `Where real bugs tend to hide`, an empty `MEMORY.md`, and two example agents, one `kind: bug` and one `kind: nit`. It refuses an existing `.mng/`; `--force` writes over the files it creates and leaves the others. Before anything is written, every generated `review.yml` and agent file is loaded as a review would load it, imports included, and a symlink on the way to any file it writes fails the command.

`mng-review init --from-macroscope` reads `.macroscope/` and leaves it untouched:

| Macroscope | `.mng/` |
|---|---|
| `correctness/correctness.md` body | `CONTEXT.md` (the starter when missing or empty) |
| its `exclude` | `skip.paths` |
| its `requires` | `needs` of every generated agent |
| `check-run-agents/<name>.md` | `agents/<name>.md`, body and `@/path` imports as they are |
| `title` | `title` |
| `include`, `exclude`, `labels`, `authors`, `targets` | `when.paths`, `when.exclude`, `when.labels`, `when.authors`, `when.targets` |
| `input: pr_metadata`, `incremental`, `full_diff` | `metadata`, `incremental`, `full_diff` |
| `input: code_object` | `full_diff`, with a warning |
| `requires` | `needs` |
| `model`, `reasoning` | dropped; the agent runs on `models.agents` |
| `maxRuns`, `maxBudget*` | dropped; `limits` cap runs and tokens |
| `approvability.md` `neverApprove` | `risk_paths` |
| its `alwaysApprove` | `skip.paths` for documentation globs only (no `!` globs); the rest is reported |
| its body | not imported |

Each agent gets `kind: nit` when its title or body mentions conventions, style or hygiene, otherwise `kind: bug`. A file name becomes lowercase with dashes for other characters; a name that is still invalid, names a built-in role or is taken gets a suffix. Line ends become LF. The output lists every dropped, changed or guessed field at the end. Exit codes: 0 when written, 2 when nothing is written.

## Benchmark

`mng-review bench <file>` replays recorded changes and compares the kept bug findings with the findings a case expects. It measures; it never passes or fails a run on the scores.

### File format, version 1

```yaml
version: 1
cases:
  - id: checkout-timeout          # unique in the file
    base: <commit sha>            # merge base of the change
    head: <commit sha>            # commit to review
    labels: []                    # optional pull request labels to simulate
    title: Fix the checkout timeout  # optional pull request title the models see
    body: |                       # optional pull request description
      Retries the charge once.
    expected:
      - id: duplicate-charge      # unique within the case
        path: src/payments/charge.handler.ts
        line: 81
        label: real               # real | intentional | false
        summary: one sentence
```

`real` is a bug the change has. `intentional` is code that looks wrong but is deliberate, and `false` a known false alarm; a finding on either counts as noise. A bare `label: false` is read as the label `false`, though YAML parses it as a boolean. Unknown keys, a missing key, a `line` below 1 and duplicate ids fail the run and name the key.

### Run

Rules come from the working tree's `.mng/`, or from `--rules-ref <ref>`, as for a review. Each case is planned and reviewed like `mng-review --base <base> --head <head>` with the case's labels, read from git by its two commits; nothing is checked out and nothing from the change runs. Each case has its own token budget and model health.

A kept bug finding matches an expected entry of its case when the paths are equal and the lines differ by at most `--line-window` (default 20). An entry matches at most one finding and a finding at most one entry; the closest pairs match first, ties go to the earlier entry. A `real` entry left unmatched is a near match when an unmatched finding sits in another file of the same directory and its title, trigger and impact contain at least half of the entry summary's content words, the share at which two reports count as one problem when findings merge. A near match never counts as found. Nits are counted apart and never match.

| Per case | Meaning |
|---|---|
| real found | `real` entries a finding matched, with the finding's validation: confirmed, unverified or unvalidated |
| near | `real` entries with a near match in a sibling file |
| real missed | `real` entries no finding matched or sat near |
| noise | `intentional` or `false` entries a finding matched |
| unmatched | findings that matched no entry and sit near none |
| rejected | bugs the validator rejected, with its reason and model |
| depth | the depth the plan chose, the rule that chose it, and the risk |
| nits | kept nits |
| tokens | per model, router included |
| wall time | plan and review |

The totals sum every case, split found into confirmed and unverified, and add recall (found over all `real` entries, near ones included) and unmatched findings per case. `--json` prints the same report as JSON. `--case <id>` (repeatable) runs a subset; an unknown id fails. `--concurrency <n>` reviews `n` cases at once, default 1.

Exit codes: 0 when every case ran, 2 on a configuration error (bench file, `.mng/`, an unknown commit) or when a case failed at the endpoint. With an endpoint failure the report is still printed.

## CI in shadow mode

The caller runs the reusable workflow on `pull_request_target` and passes `llm-url` and `llm-key` as secrets. Inputs: `runner` (default `ubuntu-latest`), `tailscale` (default `false`), `tailscale-tags` (default `tag:ci`) and `timeout-minutes` (default 20); with `tailscale` the job joins a tailnet as an ephemeral node with the `tailscale-oauth-client-id` and `tailscale-oauth-secret` secrets. The job has `contents: read` and `pull-requests: read`.

Only a pull request from the caller's own repository starts the job. It checks out the caller's base commit with its history, fetches the head commit's objects, checks out MNG Review at the workflow's own commit into a separate directory and installs it without running install scripts. It never checks out the head and never installs, builds or runs anything from the caller's repository: Bun starts in MNG Review's directory with `--no-env-file`, and git reads the caller's checkout through `MNG_REVIEW_REPO_DIR`. A tailnet node joins with `--shields-up` and then turns subnet routes off (`tailscale set --accept-routes=false`). The entry then:

1. reads the event (`GITHUB_EVENT_PATH`): base and head commits, labels, author, draft and fork flags, title and body; any other event is skipped;
2. skips a fork's pull request, loads `.mng/` from the base commit and applies `skip` (a draft is skipped unless `skip.drafts` is off or a `labels.always_review` label is set); `features` apply in the plan with the trigger `auto`;
3. probes the endpoint with `GET /models` and a 10-second timeout; unreachable, timed out, 401, 403, 429, 5xx or an unset URL end the run as "reviewer offline: <reason>" with exit 0; any other answer, such as a 404 from an endpoint without `/models`, goes on;
4. reviews base..head as `mng-review --base <base> --head <head> --rules-ref <base>` does, with title, body and labels passed to the models as fenced data;
5. writes the job summary: the verdict it would post, the risk level, the agents that ran and why, the agents skipped and why, bugs by severity with path and line (confirmed and unvalidated first, then unverified), nits, findings the validator rejected (collapsed), agents and units that did not finish, tokens per model, wall time and the engine commit. Every text from a model or the repository is escaped, and URLs become code;
6. writes the result file, which the workflow uploads as the artifact `mng-review-result` (kept 14 days), also after an invalid configuration: `version`, `status`, `engineCommit`, `run` (repository, event name, run id and attempt), `pullRequest` (number, base and head commits, target branch, author, labels, draft; no title or body), `wallMillis` of the whole entry, `verdict`, `tokens` per model, `reason` and `source` for a run that did not review, and under `review` the document `mng-review --json` prints. Every masked endpoint value is replaced before the file is written. The job summary is not exposed through the API; the artifact is.

It posts nothing: no comment, review, check run or status. Exit codes: 0 for any review result, a skip or an offline endpoint; 2 when `.mng/` at the base commit or the event is invalid, with the file and key in the summary; 1 when git cannot read the change. The endpoint URL and key are registered with `::add-mask::` and never printed. ADR 0006 records the trigger and this contract.

## CI in publish mode

`review-publish.yml` runs two jobs per pull request event. The `review` job holds the endpoint and tailnet secrets and a job token capped at `contents: read` and `pull-requests: read`; it runs the same steps as `review.yml` (both use `.github/actions/review`) plus a prepare step. The prepare step alone gets the token and no endpoint variable: it makes the checks before the probe, reads the sticky summary for the run limit and incremental input, and reads the bot's threads. The step that calls the model runs with `GITHUB_TOKEN` and `GH_TOKEN` empty and writes nothing to GitHub. A reviewed run the plan did not skip, and an offline endpoint, leave the outcome file as the `mng-review-outcome` artifact: one day of retention, at most 4 MiB, bound to the repository, the run, its attempt, the engine commit, the pull request and both commits. The `publish` job holds `contents: read` and `pull-requests`, `checks` and `statuses` write and no endpoint or tailnet secret; it starts only when the review job had something to post. It downloads this run's outcome, checks the binding against its own runner and event, and exits 1 without posting when the file is missing, too large, invalid or bound elsewhere. Re-running the publish job alone changes the attempt, so it publishes nothing; re-run the whole run, which reviews again. Publishing makes no model call. It loads the rules again from the base commit, reads the bot's review threads and the sticky summary through GraphQL, computes the lines the merge base..head diff lets it comment on, posts comments on whole files one by one, then one review as `github-actions[bot]` whose body is the summary and whose state carries the verdict and whose comments are the new line threads, or edits the body of its last review when it posted nothing new. When GitHub refuses the review's comments with 422, it posts the review again without them and lists their findings in the body. A comment the bot wrote but someone else edited is no longer the bot's. An offline endpoint writes a status review when no summary exists and otherwise marks the existing summary unfinished. A skip, an invalid `.mng/` or a git failure posts nothing, and the publish job does not start. Once the file is trusted, a GitHub error never fails the job unless the run rates (Risk rating); the job log, the job summary and the result file's `publish` field say what was posted, and a thread whose write got no answer is reported as not posted and tried again on the next run. Every text from a model or the pull request is escaped, mentions and issue and commit references included, so the bot's comments cannot link, notify or format anything they were not built to. ADR 0007.

The bot posts as `github-actions[bot]` with the job token, or as a GitHub App when the caller sets `app-slug` and the secrets `app-client-id` and `app-private-key`. Only the publish job and the sweep reference those secrets. Each mints an installation token for the calling repository with the permissions it writes with (pull requests, checks and statuses write for publishing; statuses and pull requests write for the sweep, which dismisses the bot's stale change requests), and the entry gets that token instead of the job token. Every job that runs the entry gets the slug, and a writing job fails with exit 2 before any request when the minted token's slug is not the configured one, when a token of the other mode is set, or when the slug is invalid. The owned identities are the token's identity and `identity.previous` from the rules at the base commit (the default branch for the sweep). A thread or summary counts as the bot's when an owned bot wrote it and nobody but that same bot edited it. The bot creates as its current identity, edits and deletes only what that identity wrote, and replies in any owned thread. When the newest summary review is another identity's, or there is only an old sticky comment, the run posts a new review over that marker. Every write hides the earlier reviews of owned identities and every old summary comment as outdated; an old comment GitHub refuses to hide is deleted, a review cannot be, and anything left visible is tried again by the next write; the result file's `publish` field records `cleanup` as `none`, `minimized`, `deleted` or `kept`. The commit status the sweep refreshes is the newest `MNG Review` status of an owned bot. ADR 0009.

`review-converse.yml` answers replies on the caller's schedule, and right after a reply when the caller starts it from a signal workflow through `workflow_run` (README), in three jobs. `find` holds no secret and a read-only token and lists the pull requests with a reply waiting, with the rules of the default branch. `review` and `publish` run once per listed pull request, one at a time, with the pull request and both commits from `find`'s output and their own outcome artifact; a publish leg with no outcome skips the history checkout and passes, and a pull request that closed, became a draft or moved to another head or base since `find` listed it gets nothing. `find` fails when it cannot list the pull requests or read any of them. `publish` mints a token with pull requests and statuses write (and contents read for the thread reads) and joins `mng-review-publish-<pull request>`. ADR 0009.

`review-command.yml` runs a mention command in four jobs on `issue_comment` (`created`). `authorize` holds no secret and a read-only token: it parses the command for the handle (`app-slug`, or `handle` without the app), reads the comment again, checks the commenter's role and `commands.allow` from the default branch, the named agent, the pull request and `commands.max_runs` against the summary's `manualRuns`. `reserve` holds the app key, reads the pull request again, applies the base commit's gates and counts the manual run in the summary's marker before the endpoint is used: in the newest summary review when the current identity wrote it, else in its old sticky comment when no review exists, else in a new `COMMENT` review with one status line over the carried marker (`finished: false` when there was none). `review` and `publish` work as in publish mode, with the pull request and both commits from `authorize`'s outputs, never from the event or the outcome file. Only the first attempt runs past `authorize`. ADR 0009.

## Stages

1. Engine, local: config and agent schema, routing and risk, main reviewer, declared agents, validator, CLI output.
2. Rules and benchmark: `init`, `bench`, a starter preset.
3. CI in shadow mode: reusable workflow, findings in the job summary only (see CI in shadow mode).
4. Publish and converse: threads, nit batch, summary with verdict, status, thread re-check, author replies, commands.
5. Memory and report.
