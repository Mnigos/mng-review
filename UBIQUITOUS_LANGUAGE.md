# Ubiquitous language

Canonical terms and their code names. Package and module ownership lives in `ARCHITECTURE.md`; the behaviour lives in `docs/spec.md`. This file is only the glossary. Code names marked "planned" do not exist yet.

| Term              | Code                              | Meaning                                                                                                                                                                                                                              |
| ----------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Change            | `Change`                          | What a run reviews: the commits between the merge base and the head, with their changed paths, renames and diff.                                                                                                                     |
| Unit              | `ReviewUnit` (planned)            | One function, handler or migration in the change. A risky run gives each unit its own sub-agent, up to 8 at once.                                                                                                                    |
| Agent             | `Agent` (planned)                 | A reviewer with instructions, selection rules, a model and an effort. Either the main reviewer or a declared agent.                                                                                                                  |
| Main reviewer     | `mainReviewer` (planned)          | The built-in agent that hunts for bugs across files on every code change, steered by `.mng/CONTEXT.md`.                                                                                                                              |
| Declared agent    | `.mng/agents/*.md`                | An agent a repository writes as a Markdown file with YAML front matter. `kind: bug` agents report validated bugs; `kind: nit` agents report convention checks.                                                                       |
| Router            | `RouterService` (planned)         | The model that adds agents the path rules missed, one reason each, and names what makes the change risky. It never removes an agent.                                                                                                 |
| Validator         | `ValidatorService` (planned)      | A fresh agent that tries to refute one bug finding and answers confirm, reject or unverified with evidence.                                                                                                                          |
| Unverified        | `Unverified`                      | A validator's answer for a finding whose repository premises hold but which rests on a dependency's behaviour the repository neither shows nor rules out; summary only, never blocking (ADR 0005).                                   |
| Finding           | `Finding`                         | One reported problem: path, line, severity, title, trigger, impact, evidence and an optional suggestion.                                                                                                                             |
| Fingerprint       | `toFingerprint`                   | A short hash of a finding's path and the content words of its title. Findings with the same fingerprint have the same root cause and merge; the hidden block of a thread keeps it so a later run recognises its own finding.         |
| Severity          | `Severity`                        | How bad a finding is: `low`, `medium`, `high` or `critical`, rated by the rubric.                                                                                                                                                    |
| Rubric            | `SEVERITY_CRITERIA`               | The impact criterion of each severity, shared by finders and the validator, which lowers a severity only by naming the criterion that fails.                                                                                         |
| Severity floor    | `comments.min_severity`           | The lowest severity that gets its own inline thread; findings below it go to the summary only.                                                                                                                                       |
| Nit               | `kind: nit`                       | A convention finding: batched into one review per run, capped by `comments.max_nits`, never blocking.                                                                                                                                |
| Risk              | `risk`                            | The rating of a change: `trivial`, `normal` or `risky`, derived from the router's risk signals. A change under `risk_paths` is `risky`, unless it is a repo-wide mechanical change, which is at most `normal`.                       |
| Risk signal       | `RiskSignal`                      | One reason the router gives for a risky change: a category (`access`, `money`, `stored_data`, `secrets`), a changed file and the lines in it. One signal on a reviewable changed file makes the change `risky`.                      |
| Depth             | `depth`                           | How much review a run does: `quick`, `balanced` or `deep`, or `auto` to follow the risk.                                                                                                                                             |
| Run               | `Run` (planned)                   | One review of one head commit: gate, route, find, validate, then report or publish.                                                                                                                                                  |
| Plan              | `Plan`                            | What a run will do: the runs of the main reviewer and the selected agents, the skipped ones and why, the router's additions, the risk and the depth. The `mng-review plan` command will print it.                                    |
| Shadow mode       | `ShadowRunService`                | The stage-3 workflow run: it reviews and writes the job summary, posts nothing and never fails the job on findings (ADR 0006).                                                                                                       |
| Offline           | `EndpointProbeService`            | The endpoint did not answer `GET /models` in time, refused the key, rate limited or failed; the workflow run ends neutral without a review.                                                                                          |
| Rules ref         | `--rules-ref`                     | The commit `.mng/` is read from. Locally the working tree by default; CI reads the base commit, so a pull request cannot change the rules it is judged by.                                                                           |
| Outcome file      | `OutcomeFile`                     | What a review hands to publishing: the run and pull request it is bound to, the status, the review report and the re-check proposals, as Schema-checked JSON. Publishing loads the rules and reads GitHub itself and calls no model. |
| Re-check proposal | `RecheckProposal`                 | A thread of the bot the validator no longer finds at the head, named by its node id and fingerprint. Publishing resolves it only when its own read still shows the thread open and unanswered.                                       |
| Prepared run      | `PreparedRun`                     | What the prepare step decided before the probe: `ready`, with the event, the prior run and the bot's threads, or the skip, invalid configuration or failure the run ends with. It stays in `RUNNER_TEMP` and is never uploaded.      |
| Review job        | `review` in `review-publish.yml`  | The job that holds the endpoint and a read-only token: it prepares, makes every model call, and leaves the outcome file. It never writes to GitHub.                                                                                  |
| Publish job       | `publish` in `review-publish.yml` | The job that holds the write token and no endpoint: it checks the outcome file against its own run and event and posts it, with no model call.                                                                                       |
| Bot identity      | `BotIdentity`                     | The bot account the workflow posts as: `github-actions[bot]` with the job token, or a GitHub App's bot with the app token. GraphQL names it by its slug, REST by the slug with `[bot]`.                                              |
| Owned identity    | `OwnedIdentities`                 | A bot identity whose comments and statuses count as the bot's: the current one, and those in `identity.previous` at the base commit. The bot edits only what the current one wrote (ADR 0009).                                       |
| Handle            | `getCommandHandle`                | The login commands mention: the app's slug, or the `handle` input of `review-command.yml` without the app. Never a default and never text from a comment (ADR 0009).                                                                 |
| Mention command   | `parseMentionCommand`             | A line of a new pull request comment that holds only `@<handle> review`, `review deep`, `review quick` or `run <agent>`, outside quotes, code and HTML comments. It starts a manual run once `authorize` allows it.                  |
| Manual run        | `manualRuns`                      | A run a command started: exempt from `limits.max_runs_per_pr`, counted in the summary's marker before the endpoint is used and capped by `commands.max_runs`. A run of one agent never stands for a full review.                     |
| Reply             | `ReplyItem`                       | An author's comment in one of the bot's threads. Its text is untrusted data: a claim the engine tests, never an instruction.                                                                                                         |
| Claim             | `ReplyClaim`                      | What the model read in a reply: `fixed`, `intentional` (with whether the reason holds and its evidence) or `unclear`. The engine, not the model, decides what follows (`toReplyDecision`).                                           |
| Dispute round     | `disputed`                        | One answer of the bot that disagrees with an `intentional` reply. Only these count toward `disputes.max_rounds`; past it the thread goes to the owner (`needs-owner`).                                                               |
| Memory candidate  | `toMemoryCandidate`               | One line for `.mng/MEMORY.md` from an accepted `intentional` reply: the path and the model's reason, capped, never the reply's text, without markup or mention characters. Trusted only once a person merges it.                     |
